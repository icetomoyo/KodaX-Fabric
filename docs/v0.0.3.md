# TokenHub v0.0.3 规划

| 项 | 内容 |
|---|---|
| 版本 | `v0.0.3` |
| 基线 | `9fbc9fa`：完成 v0.0.2 变更说明及管理端隐私收口 |
| 状态 | 规划中，本文只定义目标和实施边界，尚未实现 |
| 目标 | 员工用量可视化、渠道信息分层、管理员结构化上下文查看、单一日 Token 配额 |

v0.0.3 延续 v0.0.2 的权限和数据隐私约束。员工列表不恢复 API Key 字段；日志上下文不向审计员或员工开放；渠道 Key 仍只显示脱敏后的末四位。

## 1. 版本范围

本版本包含四项 P0 功能：

1. 员工管理增加“详情”，显示该员工的 Token 总体使用情况和趋势图。
2. 上游渠道页面将渠道级信息与 Key 列表分层，Key 列表顶部只保留 Key 操作。
3. 调用日志详情直接查看结构化上下文，用 Tabs 区分用户提示词、返回信息和 Skill/工具，仅管理员可见。
4. 配额策略收敛为一个按员工计算的单日总 Token 硬上限，每天指定时区的 `00:00:00` 自动进入新周期。

不在本版本内：计费、余额、Token 价格换算、全员共享总池、复杂的多级配额策略、上下文编辑或导出、Key 明文恢复。

## 2. 员工详情与 Token 用量

### 2.1 页面设计

`/admin/users` 保持当前列表字段：姓名、手机号、部门、状态、最近登录。操作列新增“详情”，放在“编辑”之前；点击后进入 `/admin/users/:id`，支持返回员工列表和浏览器前进/后退。

新建 `UserDetailView.vue`，只接受管理员角色：

- 顶部展示员工基本信息、账号状态、最近登录和当前生效的日 Token 配额；不显示任何员工 API Key 信息。
- 提供时间范围选择：今天、近 7 天、近 30 天和自定义日期。默认近 30 天，最多查询 366 天。
- KPI 卡片展示输入 Token、输出 Token、总 Token、请求数、失败数和成功率。
- 图表至少包含：
  - 每日输入/输出 Token 堆叠柱状图或折线图；
  - 每日请求数与失败数趋势图；
  - 按上游渠道/供应商的 Token 分布；
  - 按客户端模型的 Token 排名。
- 无数据时显示空状态；所有图表的汇总数字必须与同一查询范围内的明细一致。

当前 Web 依赖没有图表组件，实施时增加 `echarts` 与 `vue-echarts`，统一封装按需初始化和销毁，避免在列表页重复创建图表实例。图表只展示聚合数值，不把请求正文带到员工详情页。

### 2.2 详情接口

新增管理员接口：

```text
GET /api/admin/users/:id/usage?from=YYYY-MM-DD&to=YYYY-MM-DD
```

权限链：`requireSession` → `requirePasswordChanged` → `requireRoles("admin")`。非法员工 ID 返回 400，不存在返回 404，日期范围超过 366 天返回 400。

建议响应结构：

```json
{
  "success": true,
  "data": {
    "employee": {
      "id": 1,
      "name": "张三",
      "phone": "********1234",
      "dept": "研发部",
      "role": "employee",
      "status": "active",
      "lastLoginAt": "2026-08-05T08:00:00.000Z"
    },
    "range": {
      "from": "2026-07-07",
      "to": "2026-08-05",
      "timezone": "Asia/Shanghai"
    },
    "summary": {
      "promptTokens": 0,
      "completionTokens": 0,
      "totalTokens": 0,
      "requestCount": 0,
      "errorCount": 0,
      "successRate": 1
    },
    "daily": [],
    "byProvider": [],
    "byModel": [],
    "quota": {
      "dailyTokenLimit": 500000000,
      "usedToday": 0,
      "remainingToday": 500000000,
      "resetAt": "2026-08-06T00:00:00+08:00"
    }
  }
}
```

实现口径：

- `daily`、`summary` 优先从 `usage_counters_daily` 聚合；缺失日期由服务端补零，保证图表连续。
- `byProvider`、`byModel` 从 `request_audits` 聚合，Token 为空按 0 统计，并保留 `unknownUsageCount` 供页面提示。
- 查询和配额使用同一 `QUOTA_TIMEZONE`，避免数据库时区与页面日期不一致。
- 仅返回员工资料和用量聚合，禁止联表返回员工 API Key、Key 数量、密钥前缀或正文。

### 2.3 验收标准

- 每一行员工都能打开详情；停用员工仍可查看历史用量。
- 近 7/30 天图表的 Token 合计等于接口 `summary.totalTokens`。
- 非管理员访问详情接口返回 403，响应中不存在 API Key 字段。
- 刷新或切换日期范围不会残留上一次员工的数据。

## 3. 上游渠道与 Key 列表分层

### 3.1 现状问题

当前 `CredentialsView.vue` 将渠道协议、Base URL、状态、Key 总数、可调度数、冷却数、不可调度数和近 24 小时调用统计全部放在 Key 表上方。Key 表真正需要的只是 Key 状态和 Key 级健康信息，渠道级统计会造成重复和视觉拥挤。

### 3.2 目标布局

- 左侧渠道列表只保留：公司/模型名称、渠道状态、Key 数量和选中态。
- 右侧选中渠道的紧凑标题只保留渠道名称、编辑渠道、添加 Key 和“渠道详情”按钮。
- “渠道详情”打开抽屉或弹窗，集中展示供应商、ProductLine、协议路由、Base URL、渠道状态、Key 总数、可调度/冷却/不可调度和近 24 小时成功/失败统计。
- Key 列表顶部只显示 `Key 列表（数量）`、选择数量和批量启用/停用/测试/删除；移除顶部渠道级 KPI 卡片和重复的协议说明。
- Key 表保留 Key 脱敏标识、状态、近 24 小时成功/失败、健康、最近使用和管理员操作；不显示 Secret 明文。
- 审计员仍可只读查看渠道详情和 Key 脱敏信息，写操作继续仅管理员可用。

### 3.3 接口分层

保留现有接口兼容性，同时把页面请求拆成两类：

```text
GET /api/admin/product-lines/:id/summary
GET /api/admin/credentials?productLineId=:id
```

`summary` 返回渠道身份、协议配置和渠道级聚合统计；Key 接口只服务表格行。`summary` 的统计口径与现有 `/api/admin/credentials` 的近 24 小时窗口一致，避免页面出现两个数字。

如果第一阶段不需要拆分后端查询，也可以先复用现有响应完成 UI 分层，但前端不得再从单条 Key 行推导并展示渠道级 KPI；后续应将聚合查询迁移到 `summary` 接口。

### 3.4 验收标准

- 打开渠道后，Key 列表顶部不再出现渠道 KPI 卡片、Base URL 或协议路由详情。
- “渠道详情”中的统计只请求一次，切换 Key 不会重复请求渠道详情。
- 渠道详情和 Key 列表均不返回上游 Secret；现有批量测试、启停、删除行为不变。
- 小屏幕下渠道详情可滚动，Key 表仍能完成批量操作。

## 4. 调用日志结构化上下文

### 4.1 权限边界

调用日志列表和元数据详情继续沿用现有规则：管理员全量查看，审计员按授权范围查看元数据。新增的上下文正文单独收紧为管理员专属：

```text
GET /api/admin/logs/:requestId/context
```

该接口必须挂载 `requireRoles("admin")`，不能因为 `log_access_grants.canReadBody` 或员工本人权限而放开。审计员仍可查看时间、员工、模型、渠道、状态、Token 和错误信息，但看不到上下文 Tabs 的内容。

### 4.2 结构化响应

服务端新增 `normalizeAuditContext`，从现有已脱敏的 `request_audit_bodies` 解析不同协议的请求/响应结构，统一返回：

```json
{
  "requestId": "req_xxx",
  "truncated": false,
  "tabs": {
    "userPrompt": { "messages": [] },
    "response": { "content": [], "raw": {} },
    "skills": { "tools": [], "toolCalls": [], "skills": [] },
    "metadata": {
      "protocol": "openai_chat",
      "clientModel": "model",
      "upstreamModel": "model",
      "requestBodySize": 0,
      "responseBodySize": 0
    }
  }
}
```

规范化规则：

- 从 `messages`、`input` 或协议对应字段提取用户消息，保留消息顺序、role 和多模态块。
- 从 `choices`、`output` 或 Messages 响应字段提取返回内容，保留结构化 JSON；流式响应使用已保存的拼装结果。
- 从 `tools`、`tool_calls`、`function_call`、`skills` 等字段归一到 Skill/工具 Tab；没有相关字段时显示空状态。
- 未识别字段放在 `raw` 中，不因协议差异导致上下文丢失。
- 继承现有入库脱敏和容量上限；`truncated=true` 时显示“内容已截断”标签，不提供再次加载全文的入口。

### 4.3 页面交互

打开日志详情时，管理员自动请求元数据和 `/context`，在抽屉中使用 Tabs：

1. `用户提示词`
2. `返回信息`
3. `Skill / 工具`
4. `元数据`

所有内容直接可见，提供折叠 JSON 和复制结构化数据能力；删除现有“加载全文（计入审计）”按钮及相关文案。后端仍可静默写入 `log.read_context` 操作审计，记录操作者、Request ID 和员工归属，不在界面提示审计计费文字。

### 4.4 验收标准

- 管理员打开一条日志即可看到四个 Tabs；不再需要二次点击加载全文。
- 审计员打开同一条日志只能看到元数据，访问 context 接口返回 403。
- Authorization、Cookie、API Key、上游 Secret 等敏感字段不会出现在任一 Tab。
- Chat、Responses、Anthropic Messages、流式和非流式记录均能显示可读结构；历史缺少正文时显示明确空状态。

## 5. 配额策略收敛

### 5.1 业务口径

v0.0.3 只保留一个策略类型：`daily_total_tokens`。沿用当前按员工计数的语义，示例中的 5 亿表示“每名员工每天 5 亿 Token”；如果未来需要全体员工共享一个总池，另立需求，不在本版本隐式改变统计主体。

- 只有单日总 Token 硬上限，达到上限后拒绝后续请求。
- 每日周期按 `QUOTA_TIMEZONE` 的 `00:00:00` 切换，默认 `Asia/Shanghai`，页面必须显示当前时区和下次重置时间。
- 建议初始默认值为 `500000000`，由管理员在页面修改，不在代码中写死业务额度。
- 不提供日 Token 软上限、日请求上限、可编辑 RPM、可编辑并发和员工覆盖策略。
- 现有 RPM/并发若仍需作为网关稳定性保护，改为固定的系统级 safeguard，不再出现在“配额策略”业务配置中，也不计入策略数量。
- 不做预扣费或价格换算；以终态审计写入的 `totalTokens` 累计为准。并发在途请求可能造成少量超额，超额后后续请求拒绝，这符合当前“粗粒度治理”目标。

### 5.2 管理页面和接口

配额页面改为一个默认策略卡片：日 Token 上限、今日使用/剩余、当前时区、下次重置时间和编辑按钮。移除“新建策略”和“员工配额覆盖”两块页面。

新增简化接口：

```text
GET /api/admin/quota-policy
PUT /api/admin/quota-policy
```

更新请求只接受 `{ "dailyTokenLimit": number }`，校验为非负整数并写操作审计。旧的 `/api/admin/quota-policies`、`/api/admin/quota-overrides` 在一个兼容周期内保留只读或返回明确弃用错误，不再创建第二个策略，也不再让旧覆盖值影响运行时。

### 5.3 运行时和迁移

- 继续使用 `usage_counters_daily.total_tokens` 作为计数来源；`getEffectiveRelayQuota` 只返回日 Token 上限及固定系统 safeguard。
- `acquireRelayQuota` 和 `writeRelayAudit` 使用同一个时区计算 `quota_day`，不能继续一处使用数据库 `current_date`、另一处使用服务器本地日期。
- 种子数据确保只有一条 `is_default=true` 策略，并把旧软限和请求限置空；历史策略和 `employee_quota_overrides` 不做破坏性删除，迁移后不再参与执行。
- 在 `config.ts` 增加并校验 `QUOTA_TIMEZONE`；启动时校验失败应明确报错，避免静默落到错误日期。
- 给 `usage_counters_daily` 增加 `(employee_id, day)` 查询索引（如执行计划证明需要），保留原 `(day, employee_id)` 唯一约束。

### 5.4 验收标准

- 管理员只能看到和编辑一个日 Token 策略，不能新建第二个策略或员工覆盖。
- 员工达到当日上限后得到稳定的 `daily_token_limit_exceeded`，跨时区配置的下一个 `00:00:00` 后自动恢复。
- 详情页的“今日使用”与配额拦截读取同一计数；手动改额度不修改历史用量。
- 旧策略数据仍可迁移、回滚和审计，不因清理页面而丢失。

## 6. 实施顺序与验证

建议按以下顺序交付：

1. 先完成时区工具、员工用量聚合和管理员详情接口，补齐服务端权限与聚合测试。
2. 接入图表依赖并完成员工详情页，验证空数据、日期切换和大数值展示。
3. 增加渠道 summary 查询，调整渠道详情抽屉和 Key 列表布局，验证管理员/审计员只读边界。
4. 增加结构化上下文解析和管理员专属接口，再调整日志 Tabs；覆盖四种协议、流式截断和脱敏测试。
5. 最后迁移配额默认策略、切换运行时日界线、简化配额页，并跑配额回归测试。
6. 完成数据库迁移演练、`npm run build`、针对性 server 测试和手工权限验收；不为本版本新增无关的全量测试条目。

## 7. 版本完成定义

- 员工详情接口、路由和图表可用，且不泄露 Key 信息。
- 渠道级信息从 Key 列表顶部移出，Key 表只承担 Key 级管理。
- 调用日志上下文可直接按 Tabs 阅读，只有管理员能看到正文，界面不出现“加载全文（计入审计）”。
- 配额只剩按员工每日总 Token 硬上限，指定时区午夜切换，旧数据可兼容迁移。
- 代码、迁移、接口权限、前端构建和针对性测试均通过后，才将本文状态改为“已实现”并补充实际提交索引。
