# Token Hub 愿景功能表（手测依据）

> **来源**：[PRD.md](PRD.md) §3「Token Hub 接入管理」及 §11.1（行为）。架构落地见 [HLD.md](HLD.md) §3。  
> **用途**：功能点定义 + **人工测试对照**。测某一版时，打开 [token-hub-slices.md](token-hub-slices.md) 看该版覆盖的 `#`，用人话版当步骤和期望。  
> **不是现网说明书。** Node 试点不是 HLD 基线。  
> **现行角色**：`org_admin` / `team_admin` / `developer`。无超管。测控制台以 [v0.1.2](features/v0.1.2.md) / [v0.1.3](features/v0.1.3.md) 为准。

愿景一句话：**所有 LLM 调用进一个网关，统一路由、限流、故障转移。**

读法：上游多半是员工 / IDE / 管理员 / Space；下游多半是官方模型或自建集群，响应再回到客户端。

---

## 按能力块

| 能力块 | 覆盖功能点 | 一句话 |
|--------|------------|--------|
| 双端点零转换网关 | 1–9 | 只改 base_url，OpenAI / Anthropic 原生透传 |
| Virtual Key | 10–24 | 调用方只拿 VK，上游 Key 不出网关 |
| 渠道池化 | 25–31 | 同模型多路径，按组、按健康度切流量 |
| 路由与负载均衡 | 32–41 | 加权、优先级、同协议 Fallback；可选 ROI 选模型 |
| 限流与熔断 | 42–49 | 四维限流 + 四种超限策略 + 半开恢复 |
| 缓存 | 50–52 | Prompt 缓存 + 确定性响应缓存 |
| 流式透传 | 53–57 | SSE 原样过，断流可取消，结束后精确计量 |

骨架：员工只拿虚拟钥匙、只改 Base URL；管理员铺路、管官方 Key；Fabric 在中间选活路、刹车、记账；厂家只看见官方 Key 打来的原生请求。

## 功能总表

| # | 功能点 | 愿景怎么说 | 愿景人话版 |
|---|--------|------------|------------|
| 1 | OpenAI 兼容入站/出站 | 客户端用 OpenAI SDK 指 Fabric；转发到 OpenAI / Azure / 兼容 Provider | 你在 Cursor 里还按 OpenAI 的方式写。请求先到 Fabric，再原样转给 Azure / 官方 OpenAI / 兼容厂商。你不用接每家 SDK。 |
| 2 | Anthropic 兼容入站/出站 | 客户端用 Anthropic SDK；转发到 Anthropic / Bedrock Claude | Claude Code 还按 Anthropic 的方式写。Fabric 接到后再转给 Anthropic 或 Bedrock，中间不改成 OpenAI 格式。 |
| 3 | vLLM / 自建推理（出站） | 适配自建 vLLM 集群 API | 公司自己的 GPU 集群也可以挂上来。对你还是同一套 Base URL；Fabric 负责转到内网模型，而不是只转公有云。 |
| 4 | Fabric Native 上下文 | 任意端点用 `x-fabric-context` / `fabric_context` 传项目、任务类型等 | Space / 业务系统在请求头里多带一句「这是哪个项目、什么任务」。网关仍走原来的 chat 接口，后面好记账、好选路。 |
| 5 | 双端点零转换 | `/v1/chat/completions`、`/v1/messages` 纯透传，不改 body | 你发什么，上游就收什么。thinking、工具调用这些字段 Fabric 不翻译、不丢，避免「网关一转功能就坏」。 |
| 6 | 一把 Key 两端口 | 同一把 Fabric API Key，两个端点都能用 | 你只领一把虚拟钥匙。要调 GPT 走 OpenAI 那个地址，要调 Claude 走 Anthropic 那个地址，不用为两个协议各建一把 Key。 |
| 7 | 禁止跨协议 Fallback | 只允许同协议内（GPT-4→GPT-4o；不支持 GPT→Claude） | GPT 挂了，最多换另一个 GPT 系模型。不会在你不知情时改成 Claude——请求格式不同，硬切会错。 |
| 8 | 限流头透传 | Provider 的 `x-ratelimit-remaining` 等回给客户端 | 上游说「你还剩多少次」，Fabric 不吞掉，原样告诉 IDE。你好判断是自己被限，还是厂家在限。 |
| 9 | Embedding / Batch（V2） | `/v1/embeddings`、Batch API 路由 | 现在先保证对话。以后 Embedding、批量任务也走同一扇门，不必另搭一套网关。 |
| 10 | 上游 Key 注册与加密 | 每个 Provider 的 API Key 录入、加密保存 | 管理员把公司买来的官方 Key 存进 Fabric，磁盘上是密文。员工页面永远看不到这串 Key。 |
| 11 | 上游 Key 自动 + 手动轮换 | 配置周期轮换；轮换中不中断 | 官方 Key 到期要换新的。管理员在后台换，员工的虚拟 Key 不用改，对话不用停。 |
| 12 | 上游 Key 健康监控 | 401/403 失效告警；配额耗尽检测 | 某把官方 Key 废了或额度没了，Fabric 先发现并告警，而不是等全公司 IDE 一起报错。 |
| 13 | 上游 Key 权限范围 | Key 绑定可用模型列表和限流配额 | 这把官方 Key 只能打哪些模型、一分钟能打多少，在 Fabric 里写死，避免一把万能 Key 乱打。 |
| 14 | 上游 Key 多 Key 负载均衡 | 同一 Provider 多 Key 轮转，分摊限流 | 同一家厂商买了多把 Key。请求在它们之间摊开，避免一把打满限流、另一把闲着。 |
| 15 | 上游 Key 团队隔离 | 不同团队流量走不同上游 Key | 研发的调用不要去烧市场的那把官方 Key。谁的额度归谁，账单也好拆。 |
| 16 | VK 与上游 Key 分离 | 调用方持 `fab-xxxx`，永远看不到 Provider Key | 员工只拿 Fabric 发的虚拟钥匙。公司的官方 Key 留在网关里，离职或泄漏时先作废虚拟钥匙即可。 |
| 17 | VK 绑定链路 | VK → Project → Team → 渠道池 → Provider Key | 这把虚拟钥匙属于某个项目，项目属于某个团队，团队能用哪一批上游线路，一层层定死。后面谁花了钱能追上去。 |
| 18 | VK 预算上限 | ¥/月；超限走软/硬限制 | 这把钥匙一个月最多花多少钱。快到了先提醒，到了可以拦住，避免一张卡刷穿。 |
| 19 | VK 独立限流 | 该 Key 自己的 RPM/TPM，独立于团队 | 除了团队总闸，这把钥匙还有自己的速度限制。一个人写坏循环，不会先把全组打爆。 |
| 20 | VK 可用模型 | 该 Key 能调哪些模型 | 实习生这把钥匙也许只能用便宜模型；核心项目才能点贵模型。在钥匙上就拦住。 |
| 21 | VK 渠道池映射 | 该 Key 使用哪个渠道池 | 这把钥匙走「优质线路」还是「便宜线路」，创建时就定好。不是每次请求再临时乱选。 |
| 22 | VK 过期时间 | 到期自动失效 | 外包、试用、临时项目的钥匙可以设截止日期，到点自己作废，不用人肉回收。 |
| 23 | VK IP 白名单 | 可选，限制调用来源 | 这把钥匙只允许从公司网段或某台 CI 机器来。钥匙漏到外面，别人也调不成。 |
| 24 | VK 自助申请 + 审批 | 开发者填项目/预算/模型范围 → 团队管理员批 → 明文只显示一次 | 你在网页填项目和预算，组长点头后才拿到钥匙，而且只亮一次。和「管理员私下发官方 Key」相反。 |
| 25 | 渠道定义 | Channel = Provider + API Key + 模型列表 + 权重 + 优先级 | 一条「路」= 走哪家云、用哪把官方 Key、能打哪些模型、占多少流量、排第几优先。管理员铺路，员工不选路。 |
| 26 | 同模型多渠道池 | 如 gpt-4：Azure East / Azure West / OpenAI 直连 | 你只说要 gpt-4。背后可能有三条都能提供 gpt-4 的路，Fabric 挑一条活的走，你无感。 |
| 27 | 渠道分组 | premium / standard / bulk；项目/团队映射到分组 | VIP 项目走快而贵的路，跑批处理走便宜路。不是全公司抢同一条官方线路。 |
| 28 | 滑动窗口成功率 | 每个渠道维护最近 N 次成功率 | Fabric 盯着「这条路最近是不是老失败」，不是看一辈子平均值，刚坏就能发现。 |
| 29 | 自动禁用 / 恢复 | 成功率 &lt; 80% 禁用；定期探测成功则恢复 | 某条路上游抽风，先别把请求继续砸上去；过一会试探一下，好了再接回来。 |
| 30 | 池内流量转移 | 渠道挂了，流量切到同池其他渠道 | Azure 东挂了，还在同一个池里的 Azure 西或直连顶上。你这边还是一次 gpt-4 调用。 |
| 31 | 池级容量 | 聚合 RPM/TPM、健康渠道数、池级 RPM/TPM 上限 | 管理员能看见「这摊路加起来还能扛多少」。池也可以再加总闸，避免把上游合同额度打穿。 |
| 32 | 模型别名映射 | 一个客户端模型名 → 多 Provider + fallback 模型 | 你写 `gpt-4`。配置表说它实际可以落到哪几家、哪把 Key，不行再换哪个备用模型。 |
| 33 | 加权轮转 | 同优先级按权重分流量 | 东区 60%、西区 40%，流量按比例摊，而不是随机一把梭。 |
| 34 | 优先级故障转移 | 优先级 1 全挂 → 切优先级 2 | 先走首选（比如 Azure）。首选全挂，才动备线（比如官方直连）。不是一上来就打备用。 |
| 35 | 同协议模型 Fallback | 主模型不可用 → 配置的备用模型 | gpt-4 整条池都挂了，可以改打 gpt-4o。仍是 OpenAI 这套协议，客户端格式不用变。 |
| 36 | 延迟优先 | 选历史 P99 最低的 Provider | 最近谁回得快，就多走谁。适合对打字延迟敏感的对话，而不是死守最便宜的那家。 |
| 37 | 成本优先 | 选单位成本最低，且受 ROI 下限约束 | 默认走更便宜的路，但太便宜又老失败、老浪费的不选。不是裸比单价。 |
| 38 | 路由决策可审计 | 记选了谁、为什么、有没有 Fallback | 出了问题能回放：这次为什么去了 Azure、是不是备线顶上的。路由不是黑盒。 |
| 39 | 按渠道重试 | 次数（默认 2）、指数退避；429/5xx 重试，4xx 不重试；重试不换模型 | 上游 429/5xx，换同一模型的另一条路再试。你请求本身写错（400）不瞎重试，免得重复扣费。 |
| 40 | 简单路由（默认） | 开发者指定模型，Hub 选最佳 Provider + 自动故障转移 | V1 日常：你说要用 gpt-4，Fabric 在能提供 gpt-4 的路里挑活的、按策略分流。不用你懂厂商。 |
| 41 | ROI 优化路由（可选） | 指定任务类型，按历史 ROI 推荐模型；样本不足回退简单路由；不调用 LLM | 进阶：你说这是写代码。Fabric 查历史上这类任务谁更值，帮你选模型。数据不够就退回「你点名我选路」。 |
| 42 | 四维限流 | per-provider / per-team / per-project / per-api-key 的 RPM、TPM、并发 | 厂家合同有上限，团队有上限，项目有上限，这把钥匙还有上限。哪一层先撞上，哪一层先刹。 |
| 43 | 硬拒绝 | 超限直接 429 | 到顶了就拒，马上停。保护上游合同和预算，不假装还能打。 |
| 44 | 排队 | 超限进队等待 | 高峰先排一会儿，有空位再发，而不是直接失败。适合能等、不能丢的任务。 |
| 45 | 降级 | 超限切更便宜模型 | 额度或速度不够时，自动改用便宜模型把活干完。你可能感到模型变了，但请求没死。 |
| 46 | 突发容忍 | 令牌桶 / 漏桶 | 突然连发几下先放过，细水长流超标才刹。避免正常的一阵连问被当成攻击。 |
| 47 | 主动探测 | 定期向 Provider 发轻量请求 | Fabric 自己探一下上游还活不活。不要等员工早上打开 IDE 才发现厂家挂了一夜。 |
| 48 | 被动检测 | 按实际错误率、延迟评估 | 真正打出去的请求如果又慢又错，也算健康信号。不只靠空 ping。 |
| 49 | 熔断与半开恢复 | 错误率或 P99 超阈值熔断；半开放量，成功则恢复 | 某家连续炸，先别送人头。隔一阵放几笔试试，稳了再恢复全量。 |
| 50 | Prompt Cache | 走 Provider 的 prompt caching，降重复输入成本 | 很长的系统提示如果厂家已经缓存，下次少收一截输入费。Fabric 负责把这个能力用上，你无感。 |
| 51 | 响应缓存 | 确定性任务相同请求命中；可配 TTL 和范围 | 「把这句话翻译成英文」这种可复用的请求，不必每次都打上游。省钱、也更快。 |
| 52 | 缓存命中率监控 | 省了多少钱、命中率趋势 | 管理员能看见缓存是真省钱，还是几乎没打中。好决定要不要加大缓存。 |
| 53 | SSE 透传 | 不缓冲、不改写 Provider SSE | IDE 里字是一个个蹦出来的。Fabric 不攒完全文再给你，所以手感跟直连厂家接近。 |
| 54 | 流式中实时估 Token | 流式中用 tokenizer 估已输出量，给预算用 | 长回答还在喷的时候，预算就能大致知道烧了多少。等全部结束再看，可能已经超了。 |
| 55 | 流式中断处理 | 客户端断 → 停上游；上游断 → 通知客户端 | 你在 IDE 点停止，Fabric 立刻让厂家别再算了，避免后台继续烧 Token。厂家自己断了，也会告诉你。 |
| 56 | 流式最终计量 | 优先用 Provider `usage`；没有则用估算 | 过程中只是估算。整段结束后以厂家报的 Token 数为准记账，对账才站得住。 |
| 57 | 流式不缓存响应 | 响应体不缓存；prompt 仍可缓存 | 一边生成一边流的答案不拿来当「下次直接复读」的缓存。前面那一大段固定提示仍可走 prompt 缓存。 |

对应章节见 [PRD.md](PRD.md) §3.1–3.9、§6.1、§10.2。
