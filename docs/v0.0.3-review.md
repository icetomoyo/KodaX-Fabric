## 4. 残留问题（不阻塞开工）

### 4.1 【建议补一句】`summary.requestCount` / `errorCount` 的数据源仍有轻微打架

§2.2 写了两套表述：

- **指标定义**：`requestCount` / `errorCount` 来自 `request_audits`（含 cancelled 计入失败）。
- **跨表一致性 / 实现口径**：`daily`、`summary` **优先从** `usage_counters_daily` 聚合。

Token 侧已规定 `sum(daily.totalTokens) == summary.totalTokens`，但 **请求数/失败数** 未说明：

- KPI 与 `summary.requestCount` 是否也来自 counters？
- 若来自 counters，则与「指标定义写 audits」不一致，且 counters 的 `errorCount` 未必等于 `status <> 'success'` 的历史定义。
- 若 summary 的 Token 走 counters、请求/失败走 audits，则同一 `summary` 对象混源，需在接口注释和验收里写明。

**建议默认（实现时可直接采用）**：

| 字段 | 数据源 | 说明 |
|---|---|---|
| `summary` / `daily` 的 Token 三字段 | `usage_counters_daily` | 保持现有强一致 |
| `summary.requestCount` / `errorCount` / `successRate` | 与 Token **同源 counters**，或 **明确改为 audits** 二选一 | 不要混源 |
| 请求/失败趋势图 | 与 `summary` 同一源 | 图与 KPI 数字一致 |
| `byProvider` / `byModel` | `request_audits` | 维持跨源可偏差 |

若坚持失败定义必须按 `status <> 'success'`，则 `summary` 的请求类指标应改从 audits 聚合，并单独验收 `sum` 关系；Token 仍走 counters。

### 4.2 【小缺口】已有非 null 的 `hardTpmDay` 如何映射

迁移表只明确了 default 且 `hardTpmDay=null` → `500000000`。若现网 default 已是例如 `hardTpmDay=1_000_000`，应：

- **保留原硬限**映射为 `dailyTokenLimit`（推荐），还是
- **一律重置为 5e8**？

建议在 §5.1.1 加一行：`hardTpmDay 非 null` → `dailyTokenLimit = hardTpmDay`（仅 default 行）；非 default 策略忽略不改写业务语义。

### 4.3 【小缺口】`remainingToday` 下限

并发在途允许少量超额后，`usedToday` 可能大于 `dailyTokenLimit`。`remainingToday` 是允许负数，还是 `max(0, limit - used)`？

建议：`remainingToday = max(0, dailyTokenLimit - usedToday)`，避免前端显示负剩余。

### 4.4 【澄清即可】旧配额 API 的「只读或 410」

§5.2：`/quota-policies`、`/quota-overrides` 在兼容期「保留只读**或**返回 410」。实现时建议钉死为：

- `GET`：只读返回当前可映射视图或明确 deprecated 载荷；
- `POST/PATCH/PUT/DELETE`：统一 `410 quota_policy_deprecated`。

避免有的环境 GET 也 410、前端旧页直接挂死且无迁移提示。

### 4.5 【实现注意】`requestCount` 若走 counters，与「失败含 cancelled」

`usage_counters_daily.errorCount` 的历史写入规则需与 `status <> 'success'` 对齐；若历史上 soft 路径或 cancelled 未计入 errorCount，员工详情「失败数」会与真实审计略偏。本版若接受该偏差，可在实现注释中写「失败数以 counters 为准，可能与 audits 明细略有差异」；若不能接受，按 §4.1 建议改 audits 聚合。

### 4.6 【文档债，非本规划阻塞】PRD 尚未同步修订

规划要求在版本说明中标注 PRD §3.1 / F-25/F-26 将随 v0.0.3 修订。开工不依赖 PRD 先改完，但**发布前**应改 PRD，否则合规/测试仍可能按旧审计员可读正文验收。

### 4.7 其他极轻量项（可选）

- `byModel`/`byProvider` 的 `other` 桶响应字段形状未示例，实现时统一 `{ key: "other", totalTokens, requestCount }` 即可。
- ECharts 按需注册类型可在前端任务里约定，不必再写回规划。
- 基线 `08eac1e` 已更新说明，开工以该 commit 或更新 HEAD 为准即可。
