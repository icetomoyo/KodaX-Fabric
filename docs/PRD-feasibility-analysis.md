# KodaX Fabric PRD 可落地性分析报告

> 分析对象:`docs/PRD.md`(仅基于该文档,未参考其他资料)
> 分析日期:2026-08-17
> 结论先行:**可以落地,但必须分层落地。** Token Hub 网关层可落地性高;Token ROI 层可落地性中等,核心公式存在依赖缺口;Commerce 层技术上无难度,但商业前提未验证。

---

## 1. 总体结论

| 模块 | 可落地性 | 判断 |
|---|---|---|
| Token Hub 接入管理(§3) | ★★★★★ 高 | 成熟领域,有 LiteLLM/One API 等先例验证,"零转换透传"设计大幅降低了实现难度 |
| 计量与预算(§4.1–4.5) | ★★★★☆ 较高 | 工程上可行,预算预占与对账有细节难点但均有已知解法 |
| Token ROI(§2) | ★★★☆☆ 中 | 网关侧浪费检测可行;但 **Token 分类是核心依赖,而网关拿不到分类所需的语义信息**,这是全文最大的落地风险 |
| ROI 优化路由(§3.5) | ★★★☆☆ 中 | 算法本身简单(查表式 bandit),但输入数据质量取决于 Token ROI 层,风险传导 |
| Commerce 计费(§4.6–4.10) | ★★★★☆ 较高(技术) / ★★☆☆☆(商业) | 三层计量、Credits、账单都是确定性的记账逻辑,技术无难度;难在定价合理性与对外销售的合规资质 |
| 治理与控制台(§5、§10) | ★★★★☆ 较高 | 常规企业软件工程,量大但无技术风险;17 个界面对 V1 而言范围过大 |

一句话:**这份 PRD 的"网关部分"是一个已被市场反复验证的产品,落地没有悬念;"ROI 部分"是差异化护城河,但其数据基础(Token 分类)在纯网关视角下存在结构性缺口,需要降级设计或依赖外部报告才能兑现。**

---

## 2. 可落地性强的部分(做下去没问题)

### 2.1 零转换双端点网关——最正确的一个决策

PRD §3.1 明确"不做跨协议转换,纯透传"。这个决策直接消除了 LLM 网关类产品最大的 bug 来源(协议字段映射丢失:thinking 块、cache_control、tool_choice 等)。透传网关的实现复杂度是转换网关的几分之一,且对 Provider API 变更免疫。**这是全文降低落地风险最有效的设计。**

### 2.2 Virtual Key / 渠道池 / 熔断限流——成熟模式

- VK → Project → Team → 渠道池 → Provider Key 的映射链清晰,数据模型直白。
- 渠道健康(滑动窗口成功率 + 自动禁用/恢复)、加权轮转、优先级故障转移,都是负载均衡领域的标准做法。
- 限流四维度(provider/team/project/key)用 Redis 计数器即可实现,PRD §9.3 也已点明多副本共享状态走 Redis。

PRD 自己引用的竞品(LiteLLM 54.5k stars、One API 35.9k stars)证明这一层不存在未知技术风险。

### 2.3 预算软硬限制与 Budget Waterfall

三级瀑布(项目→团队→企业)+ 80%/100% 软硬限制,是确定性规则,实现即"查余额、扣减、告警"。402/429 错误模型(§6.3)定义清晰。唯一细节难点是高并发下扣减的原子性,Redis Lua 或 PG 行锁均可解决。

### 2.4 边界划分自觉

§1.4"不做的事"和附录"归属其他体系的能力"写得很克制:不做协议转换、不调 LLM 做优化、不做 Agent Runtime、不算 GPU 完全成本、认证归 Space。**PRD 主动砍掉的东西恰好都是最容易失控的部分**,这说明范围控制是认真做过的,显著提升整体可落地性。

## 3. 落地风险点(按严重程度排序)

### 3.1 【最高风险】Token 分类体系的数据来源缺口

§2.2 把输入 Token 分成 5 类(System Prompt / User Query / Context / Tool Result / Injected),输出分 4 类,每类赋权重,这是 Token ROI 公式(§2.3)的唯一输入。问题在于:

- **网关看到的是一个 messages 数组,协议层没有"这段是 System Prompt、那段是注入的文件"的标注。** system role 可辨认,但 Context/Tool Result/Injected 的区分依赖调用方的组装语义,纯透传网关无从得知。
- Provider 返回的 usage 只有 input/output/cached/reasoning 的总数,**没有按 message 段的 Token 细分**。要按段计 Token 需要网关自己跑 tokenizer,且对不同模型要用不同 tokenizer,精度和性能都有代价(与 §9.2 "路由延迟 P99 < 50ms" 目标冲突)。
- 输出侧的 Final Output / Tool Call / Thinking 区分相对可行(协议里有结构),但输入侧的五分类在没有调用方配合(`fabric_context` 或 Runtime 报告)时**基本只能靠启发式猜测**。

**影响**:北极星指标 Token ROI 的分子分母都建立在分类之上。分类不准,ROI 数字就是伪精确,进而污染 ROI 优化路由(§3.5)的推荐。

**建议**:PRD 应明确 V1 的分类降级策略——例如 V1 只做协议层可确定的三分类(system / 非 system 输入 / 输出内的 tool_call、thinking、text),五分类标注要求调用方通过 `x-fabric-context` 显式传入,未标注时 ROI 标记为"低置信度"。当前 PRD 对此完全未提,是文档层面最需要补的洞。

### 3.2 【高风险】价值权重是拍脑袋数字,且直接决定北极星指标

0.3 / 1.0 / 0.5 / 0.2 / 0.4 这些权重没有任何标定方法说明。两个后果:

1. 同一份流量,权重表一改,ROI 数字整体平移——**客户无法用它做跨期对比,除非权重版本化**(Pricebook 有版本管理,权重表却没有,这是不一致的)。
2. "type_weight ≥ 0.3 视为有价值"的阈值使 Tool Result(0.2)永远算浪费,而 Tool Result 恰恰是 Agent 工作流的主要 Token 构成。这会系统性地把 Agent 流量的 ROI 压低,客户会质疑指标公平性。

**建议**:权重表必须版本化 + 可按企业配置(PRD §2.3 只对 Outcome 倍率说了"可调",Token 权重没说);上线初期建议 ROI 仪表盘同时展示"未加权原始比例",避免指标被质疑时无退路。

### 3.3 【高风险】流式 + 故障转移 + 计量精度三者互相挤压

单独看每条都可行,组合起来有硬冲突:

- §9.2 要求"实时计量精度与 Provider usage 误差 < 1%",但 §3.9 承认流式中途只能 tokenizer 估算,部分 Provider 的 SSE 流在客户端中断时**不会返回 usage**,此时"< 1%"无法保证。PRD 说"无 usage 时用估算值",那么精度目标就应该对这类请求豁免——文档未写。
- 流式响应开始下发后无法再做故障转移(客户端已收到半截流),"Provider 故障 → 自动转移 < 5s"(§9.2)只对首字节前有效。这个约束应写明,否则会被当成 SLA 承诺。

### 3.4 【中风险】文件级成本归因的适用面被高估

§2.4 的示例(按文件分摊 Run 成本)很有说服力,但它依赖三个条件同时成立:① 调用方用标准 tool_use/function_call 格式;② 工具是 edit/write/read 这类带文件路径的;③ 请求带 `fabric_context` 能串成 Run。PRD 在 §2.4 的"限制"注里其实承认了这些,但 §11 的卖点总结里仍把"文件级归因"当成普适能力宣传。**实际落地时,大量流量(chat、非 Agent 调用、自定义工具 schema)不满足条件,这个功能的覆盖率可能只有流量的一小部分。** 落地没问题,但要管理预期,否则验收时会被认为"功能没做出来"。

另外注意:文件级归因要求解析请求/响应正文,而 §5.3 的 Zero Retention / Metadata Only 模式下正文不落盘——归因结果(文件路径)本身算不算敏感元数据、在哪档模式下可保存,PRD 没有界定,存在合规灰区。

### 3.5 【中风险】V1 范围仍然偏大

虽然 PRD 有 Phase 1–5 的路线(§11.4),但正文大量能力没有标注属于哪个 Phase:预算预占(§4.4)、供应商对账(§4.5)、五档数据保存 + 归档分级 + Legal Hold(§5.3)、17 个控制台界面(§10.2)、响应缓存、排队限流……这些每一项都是数周级工程量。**文档开头已说明现网是 v0.1.3 三角色、无超管无多租户,说明团队自己也清楚 PRD 是愿景而非排期**——但 PRD 内部最好显式给每个能力打 Phase 标签,否则"可落地"会被误读为"V1 可交付"。

### 3.6 【中风险,商业而非技术】Commerce 层的前提未验证

三层计量、Credits 倍率、split/markup、利润追踪,记账逻辑全是确定性的,技术落地无难度。风险在:

- **超卖利润模型**成立的前提是"客户平均用不完额度",这需要真实用量数据支撑 split 比例的定价,V1 没有数据,初期套餐定价基本靠猜,可能定亏。
- 对外卖 Token(SaaS 模式)在多数司法辖区涉及**转售云服务/增值电信类合规问题**,以及上游 Provider TOS 是否允许转售——PRD 完全未提,这是 SaaS 路径落地前必须回答的非技术问题。
- 倍率表(§4.7)与 Pricebook(§4.6)通过"标准价 = 倍率 × Credit 单价"强绑定,Provider 频繁调价时,倍率、Credit 单价、标准价三者的版本联动维护成本不低,建议只保留一个自由变量。

### 3.7 【低风险】其他小问题

- §4.1"四套账本"表格中,"结果账"一行被夹注打断,文档结构错乱(第 440 行),是编辑事故。
- ROI 优化路由(§3.5)的 task_type 依赖调用方自觉传入,受控词表 6 个值,实际数据可能大量落在默认/空值上,bandit 的分组样本会很稀疏——算法可落地,冷启动周期要按"季度"而非"周"预期。
- §9.3"返回最近一次成功的缓存响应"作为 Provider 全挂时的降级,对 LLM 这种非确定性接口价值极低且有误导风险,虽已限定"确定性任务 + x-fabric-stale 头",建议直接砍掉,减少一个安全隐患面。

## 4. 内部一致性检查

| 检查项 | 结果 |
|---|---|
| "不调用 LLM"约束 vs 各优化功能 | ✅ 一致,浪费检测/路由优化都注明用统计方法 |
| "零转换" vs Fallback 设计 | ✅ 一致,Fallback 明确限定同协议内 |
| Zero Retention vs 网关需读正文 | ✅ 已用"内存瞬态处理"注解自洽(§5.4);但与文件级归因的交叉未覆盖(见 3.4) |
| Pricebook 版本化 vs 权重表版本化 | ⚠️ 不一致,价格有版本管理,ROI 权重表没有 |
| 计量精度 <1% vs 流式无 usage 场景 | ⚠️ 冲突未处理(见 3.3) |
| 愿景(四角色 17 界面) vs 现网(三角色) | ✅ 文首已声明,自觉性好 |

## 5. 落地建议(按优先级)

1. **补 Token 分类的 V1 降级方案**:明确"协议可确定的粗分类"为默认,五分类依赖 `x-fabric-context` 显式标注,ROI 带置信度标记。这是护城河能否兑现的关键,应在写代码前定案。
2. **ROI 权重表版本化 + 企业可配置**,并在仪表盘保留未加权视图。
3. **给 PRD 每个能力打 Phase 标签**,把 §5.3 归档分级、§4.4 预占、17 界面中的大半明确推到 Phase 3+,保护 Phase 1/2 的交付节奏。
4. **修正 §9.2 SLA 表述**:计量精度对"流式中断无 usage"豁免;故障转移限定首字节前。
5. **Commerce 启动前完成两个非技术验证**:上游 Provider 转售条款审查;基于 Phase 1 真实用量数据回测 split/markup 定价,再开放对外套餐。
6. 修复 §4.1 表格结构错乱等文档缺陷。

---

## 6. 最终判断

**这个项目可以落地。** 理由:

- 核心网关层(Phase 1–2)技术路线保守(透传、PG+Redis、单进程起步)、有大量开源先例、且现网已有 v0.1.3 在跑,证明团队具备交付能力。
- 差异化的 ROI 层不是"做不出来",而是"数据输入达不到 PRD 描述的精细度"——通过降级分类 + 置信度标注 + 调用方标注协议,可以交付一个诚实版本,再随 Runtime 集成逐步逼近愿景。
- Commerce 层技术零风险,落地节奏应由商业验证(定价数据、转售合规)而非工程进度决定。

最大的失败模式不是技术做不出来,而是:**把愿景当排期,17 个界面和五档保存策略挤进早期版本,拖垮网关主线;或者 ROI 数字因分类不准而失去客户信任,护城河变成负资产。** 只要按 Phase 纪律推进、并先解决 3.1 的分类缺口,落地路径是清晰的。
