## 1. 产品背景与定位

### 1.1 背景

公司采购并分配了多份官方大模型服务凭证。按员工一人一把上游 Key 使用时，存在以下问题：

- 额度分散，部分员工额度不足时，其他凭证仍可能长期闲置；
- Key 散落在个人环境，难以统一保管、停用和授权；
- 缺少统一的调用记录，无法系统回答谁在何时调用了什么模型、消耗了多少 Token、请求和响应内容是什么；
- 不同供应商、产品线和兼容协议的接入方式不一致，员工配置成本较高；
- Coding Plan 等套餐凭证存在授权和厂商条款边界，不适合默认全员混用。

### 1.2 产品定位

> TokenHub 是公司内网的 LLM 统一网关、官方凭证池调度系统和员工级调用审计台账。

TokenHub 面向公司内部员工，不提供外部注册、API 转售、充值、余额账户或倍率计费。员工只持有 TokenHub 签发的内部 API Key，上游凭证由管理员集中托管。

### 1.3 核心价值

1. **统一接入**：员工使用统一 Base URL 和内部 API Key 接入多家官方模型服务。
2. **凭证池化**：在员工选择的上游渠道内调度多条可用凭证，提高采购利用率。
3. **渠道隔离**：每把员工 Key 固定绑定一个上游渠道和一种兼容协议，模型解析、重试和亲和均不得跨渠道。
4. **权限治理**：公共渠道面向员工共享，授权渠道按凭证授权范围开放。
5. **调用审计**：记录调用主体、模型、渠道、用量、终态及经过安全处理的请求和响应正文。
6. **不计费治理**：通过单日总 Token 硬上限与系统级 RPM/并发 safeguard 控制资源使用，不建立商业计费体系。

### 1.4 成功标准

| 维度 | 成功标准 |
|---|---|
| 接入 | 员工只需配置 TokenHub Base URL、内部 API Key 和模型名即可调用 |
| 共享 | 一个渠道可托管多条上游凭证，并在该渠道内按策略共享额度 |
| 隔离 | 绑定渠道 A 的 Key 在模型查询、调用、重试和亲和场景中均不能命中渠道 B |
| 权限 | 公共池和授权池均在每次请求时校验，不因持有 Key 获得额外权限 |
| 审计 | 通过 API Key 鉴权后的所有终态均可追溯到员工、内部 Key、客户端模型和结果；选出候选后记录渠道、凭证和上游模型，选出候选前记录该 Key 的绑定渠道 |
| 管控 | 支持按员工的单日总 Token 硬上限，以及系统级 RPM、并发 safeguard |
| 安全 | 上游 Secret 不出现在员工接口和日志中；员工 Key 明文仅在创建成功时向创建员工本人展示一次，员工和管理员均不能再次读取 |
| 部署 | 支持公司内网部署，PostgreSQL 与 Redis 使用独立实例或独立逻辑空间 |

## 2. 产品目标与边界

### 2.1 产品目标

1. 集中托管公司采购的官方 API Key 和受控套餐凭证。
2. 支持智谱国内/国际、MiniMax、Kimi、DeepSeek 等官方供应商扩展。
3. 支持 OpenAI Chat Completions、OpenAI Responses 和 Anthropic Messages 三类原生协议。
4. 支持公共池与授权池两种共享模式。
5. 提供管理员、审计员和员工相互隔离的工作入口。
6. 提供员工自助 Key、个人用量和个人调用记录。
7. 提供渠道、凭证、授权、配额、日志、操作审计和运营概览管理能力。
8. 在安全脱敏与单条容量上限内长期保留请求和响应审计正文，超限数据保留摘要和截断标记。

### 2.2 产品边界

| 不纳入范围 | 说明 |
|---|---|
| 对外公开注册与 API 售卖 | TokenHub 仅服务公司内部账号 |
| 充值、套餐、余额、预扣费、退款和倍率计费 | 产品只做用量治理，不做商业计费 |
| 员工自助注册 | 账号仅由管理员创建或导入 |
| 海量供应商通用中转 | 仅接入公司实际采购且经过验证的官方服务 |
| 跨协议转换 | Key 绑定的协议与上游原生协议一致，不做 Chat、Responses、Messages 互转 |
| 跨渠道容灾 | 员工 Key 的所有候选始终限定在绑定渠道内 |
| Responses 后台任务与 Conversation 托管 | 当前只支持同步原生透传和流式透传 |
| 网页聊天工作台 | 员工调用入口为 IDE、CLI 或脚本；网页 Playground 属于后续能力 |
| 替代公司 SSO | 当前使用手机号和密码，SSO/OIDC 属于后续能力 |

## 3. 用户、角色与账号

### 3.1 角色定义

| 角色 | 页面入口 | 能力范围 |
|---|---|---|
| 管理员 `admin` | `/admin/*` | 员工管理、渠道与凭证管理、模型与授权、配额、全量日志、操作审计和运营概览 |
| 审计员 `auditor` | `/admin/*` 的只读子集 | 查看全局运营概览、上游渠道只读信息，以及授权范围内的调用记录**元数据**；正文不对审计员开放 |
| 员工 `employee` | `/me/*` | 修改密码、创建和删除自己的 API Key、查看自己的用量与调用记录 |
| 调用方 | `/v1/*` | 使用有效的员工 API Key 调用与查询模型，不具有页面权限 |

审计员不能创建或修改员工、渠道、凭证、授权、配额和系统设置。管理员和审计员均不能列出员工 API Key 或读取其明文；概览中的人员排名和错误摘要属于运营统计，调用明细仍受日志授权控制。**（v0.0.3）管理端调用正文仅管理员可见，审计员不可见。**

### 3.2 角色隔离

- `/api/me/*` 只允许已改密的 `employee` 访问；
- `/api/admin/*` 按 `admin` 和 `auditor` 的权限子集授权；
- `/v1/*` 只接受状态有效、所有者为 active `employee` 的内部 API Key；
- `admin` 和 `auditor` 不能创建调用 Key，也不能进入员工端；
- `employee` 不能进入管理端；
- 页面不提供管理端和员工端之间的切换入口；
- 用户从 `employee` 变为 `admin` 或 `auditor` 时，系统在同一事务内 revoke 其全部 active 调用 Key；该用户再次成为 `employee` 时，已 revoke 的 Key 仍保持失效。

### 3.3 账号规则

| 规则 | 产品要求 |
|---|---|
| 登录标识 | 手机号唯一 |
| 建号字段 | 姓名、手机号、初始密码、部门（可选）、角色 |
| 开户方式 | 管理员单个创建或批量导入 |
| 首次登录 | `must_change_password = true`，改密前不能使用业务页面或模型代理 |
| 账号状态 | 停用账号不能登录，其名下调用 Key 不能通过代理鉴权 |
| 密码重置 | 管理员可重置，用户下次登录必须改密 |
| 员工 API Key | `th_...`；哈希用于鉴权，完整明文仅在创建响应中向创建员工本人返回一次 |
| 上游凭证 | 仅管理员维护，加密存储，界面不回显完整 Secret |

### 3.4 员工 API Key 安全规则

1. 员工创建 Key 时依次选择上游渠道、兼容协议并填写名称。
2. Key 只在创建成功结果中向发起创建的员工本人展示一次，员工需当场保存。
3. 员工 Key 列表只展示名称、前缀、绑定渠道、协议、状态和时间，不提供明文读取接口。
4. 绑定渠道和协议创建后不可编辑；员工需要调整时删除 Key 后重新创建。
5. 管理员员工列表只展示员工账号主表中的非敏感列表字段，不返回 Key 数量、列表、前缀、绑定信息或明文。
6. 管理员和审计员均无员工 Key 列表及明文读取接口，不能查看或复制员工 Key。

## 4. 核心业务流程

### 4.1 管理员配置上游

1. 选择供应商模板或录入供应商。
2. 创建 API 或 Coding Plan 产品线，设置启用状态、共享模式和自动路由开关。
3. 在产品线下批量录入一条或多条加密上游凭证。
4. 为凭证声明兼容协议、优先级、权重和状态。
5. 执行连接测试和模型发现，按需配置显式模型路由。
6. 对 `grant_only` 产品线配置员工级凭证授权。

### 4.2 管理员开户

1. 管理员单个创建或批量导入员工。
2. 员工使用手机号和初始密码登录。
3. 员工完成强制改密。
4. 员工进入 API Key 页面创建调用 Key。

### 4.3 员工创建 API Key

1. 页面加载当前员工可选择的上游渠道。
2. 员工选择渠道后，页面展示该渠道对当前员工可用的兼容协议。
3. 员工选择协议、填写 Key 名称并提交。
4. 服务端再次校验渠道、授权和协议可用性，创建绑定 Key。
5. 页面向发起创建的员工本人一次性展示完整明文；关闭结果后不能再次读取。

### 4.4 员工调用模型

1. 员工在 IDE、CLI 或脚本中配置 TokenHub Base URL 和内部 API Key。
2. 调用方通过 `/v1/models` 查询该 Key 当前真实可调用的模型。
3. 调用方发起与 Key 协议一致的请求。
4. 网关完成 Key 鉴权、角色校验、渠道与授权复核、配额检查、模型解析和凭证调度。
5. 网关将请求原生转发至绑定渠道，按策略在该渠道内重试。
6. 网关透传响应并记录用量、正文、终态和重试轨迹。

### 4.5 审计查阅

1. 员工查看自己的调用列表和审计正文。
2. 管理员检索全量调用记录。
3. 审计员按日志授权范围查看调用元数据；审计员不可查看正文，正文仅管理员可见。
4. 查看他人正文、授权变动和渠道管理操作均写入操作审计。

## 6. 页面信息架构

### 6.1 员工端 `/me`

| 页面 | 主要内容 |
|---|---|
| 工作台 | 今日/本月用量、Base URL、鉴权头和接入示例 |

### 7.3 员工 API Key 接口契约

创建请求必须提供 `name`、`productLineId` 和 `protocol`，服务端不设置默认渠道或协议。`name` 去除首尾空白后长度为 1–100，`productLineId` 为正整数，`protocol` 必须属于渠道对当前员工返回的最新兼容协议集合。

| 场景 | HTTP 状态 | 错误码 |
|---|---:|---|
| 字段缺失、类型或枚举错误 | 400 | `invalid_request` |
| 渠道不存在、当前员工无权使用或渠道已停用 | 404 | `upstream_channel_unavailable` |
| 提交协议不在渠道的最新兼容集合 | 400 | `channel_protocol_incompatible` |

创建成功响应包含完整 Key、ProductLine、协议和渠道摘要；完整 Key 仅在本次响应中向发起创建的员工本人展示。员工列表接口不返回明文，员工侧不注册 reveal 路由，删除接口同时记录名称、协议和渠道摘要。

员工管理列表只返回员工账号主表中的非敏感列表字段，不返回 `activeApiKeyCount` 或其他 Key 信息。服务端不提供管理员列出员工 Key 或读取员工 Key 明文的接口，管理端不能查看或复制员工 Key。

## 8. 渠道绑定与调度规则

### 8.1 概念模型

```text
Provider（供应商）
  └─ ProductLine（上游渠道：api | coding_plan）
       ├─ UpstreamCredential（具体上游凭证，可声明多个兼容协议）
       ├─ CredentialEmployeeGrant（员工对凭证的授权）
       └─ ModelRoute / DiscoveredModel（显式路由 / 已发现模型）

EmployeeApiKey（员工内部 Key）
  └─ product_line_id + protocol
```

### 8.2 共享模式

| 共享模式 | 可见与授权规则 | 典型用途 |
|---|---|---|
| `public_pool` | active 员工可使用渠道内符合条件的凭证 | 官方 API 公共额度池 |
| `grant_only` | 只使用当前员工被明确授权的凭证 | Coding Plan 或受限渠道 |

渠道内共享不表示跨渠道共享。一把绑定 Key 只能使用其 `product_line_id` 下的候选凭证。

### 8.3 可选渠道与兼容协议聚合

员工可选择的渠道必须同时满足：

1. Provider 和 ProductLine 均为 active；
2. `public_pool` 至少有一条符合条件的渠道凭证，或 `grant_only` 至少有一条当前员工被授权的符合条件凭证；
3. 参与聚合的凭证有效状态为 `active` 或 `cooling`，且 `weight > 0`；
4. `disabled` 和 `auto_disabled` 凭证不参与聚合；
5. 兼容协议为可见凭证声明协议的并集；空协议集合不提供任何协议能力；
6. 返回的 `credentialCount` 只统计当前员工可见且参与协议聚合的凭证；
7. 员工渠道接口不读取或返回上游 Secret、上游 Base URL、未授权凭证数量和内部健康详情。

渠道按 Provider 名称、ProductLine 名称和 ProductLine ID 稳定排序。只读查询按时间计算 effective credential status：冷却时间为空或已到期的 `cooling` 视为 active，尚未到期的视为 cooling；查询本身不回写凭证状态。

### 8.4 Key 渠道绑定

每把员工 Key 必须同时关联一个非空 `product_line_id` 和一个协议。数据库外键、创建接口、鉴权 principal 与 Relay 调度均以该 ProductLine 为唯一渠道边界。系统不存在未绑定渠道的员工 Key，也不存在运行时全局候选池模式。

### 8.5 绑定与授权

绑定渠道不产生授权。每次模型查询和调用均实时复核：

- 员工、Provider 和 ProductLine 状态；
- ProductLine 的 `share_mode`；
- `grant_only` 下的凭证授权关系；
- 凭证状态、冷却时间、权重和协议能力；
- 模型路由或模型发现结果。

授权撤销、共享模式调整、渠道停用、凭证停用、权重归零或协议移除应在后续请求中立即生效，不能退回其他渠道。

### 8.6 模型解析

员工 Key 的模型解析顺序如下：

1. 在绑定 ProductLine 内查找 `client_model` 对应的 enabled 显式路由；
2. 存在 enabled 显式路由时，只按显式路由解析；即使路由权重为 0 或没有匹配协议的可用凭证，也不回退到自动发现；
3. disabled 显式路由不参与判定；
4. 不存在 enabled 显式路由时，只有在绑定 ProductLine 开启 `allow_auto_route` 且 `discoveredModels` 包含该模型时，才允许自动路由；
5. 其他 ProductLine 的同名显式路由和发现结果不得影响当前 Key。

### 8.7 凭证选择、重试与亲和

1. 候选先按模型路由 priority，再按凭证 priority 分层。
2. 同一优先级内按 `routeWeight × credentialWeight` 加权选择。
3. 一次请求不重复尝试同一凭证，默认最多尝试 3 条候选。
4. 401/403 将凭证标记为 `auto_disabled`；429 进入冷却；5xx 和首字节前的网络错误切换候选；400 直接返回。
5. 流式响应首字节发出后不再切换凭证；客户端断开时取消上游请求。
6. 所有候选和重试都限定在绑定 ProductLine。
7. Responses `previous_response_id` 必须严格匹配记录中的 credential、ProductLine 和 upstream model，不重新分配凭证，并且记录必须与 Key 的绑定 ProductLine 一致。
8. 亲和记录不存在时返回 `409 response_affinity_not_found`；记录对应候选当前不可用时返回 `503 response_affinity_unavailable`。

### 8.8 模型列表一致性

`GET /v1/models` 与实际调用共用同一套员工状态、Key 协议、绑定 ProductLine、共享模式、授权、凭证状态和模型解析规则，只列绑定渠道当前可调用的模型，不展示其他渠道的同名模型。

模型列表按查询时的 effective credential status 计算，属于只读操作，不回写 cooling 或其他凭证状态。

### 8.9 确定性错误契约

| 场景 | HTTP 状态 | 错误码 |
|---|---:|---|
| Key 无效、过期、已失效，或所有者状态/角色不允许调用 | 401 | `invalid_api_key` |
| Provider、ProductLine 或运行时渠道授权不可用 | 503 | `bound_channel_unavailable` |
| 绑定渠道内不存在目标模型 | 404 | `model_not_found` |
| 匹配凭证全部处于有效冷却期 | 429 | `model_channels_cooling`，响应带 `Retry-After` |
| 模型已配置但无可用匹配凭证 | 503 | `model_unavailable` |
| `previous_response_id` 亲和记录不存在 | 409 | `response_affinity_not_found` |
| 亲和记录对应候选当前不可用 | 503 | `response_affinity_unavailable` |

错误响应使用请求协议对应的 OpenAI 或 Anthropic 原生 envelope，不暴露上游 Secret、Base URL、未授权渠道和凭证细节。

### 8.10 配额治理

| 类型 | 行为 |
|---|---|
| 业务配额 | 每名员工共用一个单日总 Token 硬上限；达到上限后拒绝后续请求 |
| 日界线 | 按 `QUOTA_TIMEZONE` 的 `00:00:00` 进入新周期，默认 `Asia/Shanghai` |
| RPM safeguard | 按员工限制每分钟请求数，由 `RELAY_SAFEGUARD_RPM` 固定配置 |
| 并发 safeguard | 按员工维护 Redis 并发租约，由 `RELAY_SAFEGUARD_MAX_CONCURRENCY` 固定配置 |

配额以员工为主体执行，不提供多策略、员工覆盖、日请求上限或日 Token 软上限。用量以终态审计累计为准，并发在途可能产生少量超额；超额后后续请求拒绝。配额只用于资源治理，不生成金额或账单。数据库仅保留单日 Token 上限与实际用量计数。

## 9. 审计、安全与合规

### 9.1 调用审计内容

**审计元数据**包括：员工、内部 API Key、协议、绑定 ProductLine、请求时间、客户端模型、上游模型、Provider、凭证标识/末四位、流式标记、终态、HTTP 状态、错误码、Token 用量、原始 usage、耗时、重试轨迹、IP、User-Agent 和请求路径。

**审计正文**包括：经过安全脱敏的请求体、响应体或流式拼装结果，以及可选的脱敏 Header。Authorization 和 Secret 不得入库。

请求在选出上游凭证前失败时，仍记录内部 Key 的绑定 ProductLine、协议和确定性错误结果。

### 9.2 终态覆盖

- 通过 API Key 鉴权后，成功、上游失败、参数错误、配额拒绝、绑定渠道凭证池不可用和客户端取消均记录审计；
- Responses 流以 `response.completed`、`response.failed`、`response.incomplete` 或 `error` 判定终态；
- Messages 流以 `message_stop` 或 `error` 判定终态；
- 工具调用和增量参数保持上游原生事件结构。

### 9.3 可见性

| 主体 | 审计元数据 | 审计正文 |
|---|---|---|
| 员工 | 仅自己的调用 | 可查看自己的已保存正文 |
| 审计员 | 日志授权范围 | 不可见 |
| 管理员 | 全部 | 全部；读取他人正文写操作审计 |

### 9.4 保留与容量

- 已写入 PostgreSQL 的审计记录不自动删除；
- 单条正文受 `AUDIT_BODY_MAX_BYTES` 等安全容量限制；
- 超限内容保存 preview、截断标记和完整元数据，不宣称保留超出上限的全部字节；
- 长期容量压力通过归档或对象存储处理，归档后的业务可查能力属于生产加固范围。

### 9.5 Secret 与 Key

- 上游 Secret 使用独立加密密钥加密存储；
- 员工 API Key 使用哈希鉴权；加密存储字段不对员工或管理员提供查询、解密或明文返回能力；
- 员工渠道查询只使用非敏感元数据，不解密上游 Secret；
- 管理员员工列表不显示或返回任何员工 Key 数量、列表或明文；
- 员工 Key 创建、删除的审计详情包含 ProductLine 和协议；查看他人正文、修改凭证和授权等敏感动作写入 `ops_audit_logs`；
- 生产环境必须使用内网 HTTPS，并限制数据库、备份和加密密钥访问权限。

### 9.6 Coding Plan 合规

Coding Plan 默认使用 `grant_only`。多账号、多终端或共享套餐凭证可能受供应商条款限制，管理员应在录入前确认授权范围。产品线级独立重试策略交付前，Coding Plan 使用系统统一重试上限。

- 手机号登录、强制改密、员工单建/批量导入、编辑、启停和密码重置；
- 员工按渠道、兼容协议和名称创建 Key，支持本人一次性明文、绑定渠道列表、删除和哈希鉴权；管理端不返回员工 Key 信息；
- 管理端员工用量详情、渠道分层详情、结构化日志上下文、单一配额、概览和操作审计页面。

**上游与代理**

- Provider、ProductLine、UpstreamCredential 三层结构；
- 上游凭证批量录入、加密存储、连接测试、模型发现、协议、状态、优先级、权重和员工授权；
- 绑定渠道内的 `GET /v1/models`、Chat Completions、Responses、Responses compact、Messages 和 Messages count_tokens；
- 显式模型路由与已发现模型自动路由；
- JSON 与 SSE 原生透传、首字节前重试、客户端断开取消上游；
- 401/403 自动停用、429 冷却、5xx/网络错误切换和 400 不重试；
- 绑定渠道内重试与 Responses `previous_response_id` 严格凭证亲和。

**治理与审计**

- 按员工的单日总 Token 硬上限，以及 Redis RPM、并发系统级 safeguard；
- 调用元数据、受容量限制的请求/响应正文、usage、重试轨迹和终态审计；
- 员工个人正文、管理员全量结构化上下文、审计员授权范围内元数据；
- 当日请求/Token/失败、Top 员工、供应商分布和最近错误概览。

## 14. v0.0.1 验收标准

1. 未选择渠道时不能选择协议或提交；选择或切换渠道后，旧协议值被丢弃并默认选中该渠道的第一项兼容协议。
2. public_pool、grant_only、停用渠道及各凭证状态的渠道显示和协议聚合结果正确。
3. 创建 Key 后，ProductLine、协议、Key 列表和审计信息一致；数据库拒绝任何无渠道 Key。
4. 员工明文只在创建响应中向本人出现一次；员工无明文找回接口；管理员员工列表不返回任何 Key 信息，且员工 Key 列表与明文读取接口均不可达。
5. admin/auditor 不能访问 `/me` 或创建调用 Key；employee 不能访问管理端。
6. employee 角色退出时 active Key 全部 revoke，再次成为 employee 时不自动生效。
7. 两个渠道配置同名模型时，绑定渠道 A 的 Key 在所有协议入口、重试和 affinity 场景中均不能命中渠道 B。
8. `/v1/models` 只列绑定渠道中当前可调用的模型，列表与实际请求结果使用相同过滤口径，并且查询不回写凭证状态。
9. 显式路由和绑定渠道内自动发现的优先关系符合第 8.6 节。
10. grant 撤销、共享模式调整、渠道/凭证停用、权重归零和协议移除在后续请求中生效，且不跨渠道。
11. 渠道、模型、冷却和凭证不可用场景返回第 8.9 节定义的状态码和错误 envelope。
12. 员工渠道接口不解密或泄露 Secret、上游 Base URL和未授权凭证数量。
13. 所有 Key 必须关联 ProductLine；被 Key 引用的 ProductLine 不能被删除或置空。
14. 渠道列表返回后发生授权、状态或协议变化时，创建接口重新校验并返回第 7.3 节定义的错误，不创建失效绑定。
15. Chat、Responses、Responses compact、Messages、Messages count_tokens 和 `/v1/models` 全部通过渠道隔离验收。

## 15. 风险与依赖

### 15.1 主要风险

| 风险 | 影响 | 应对 |
|---|---|---|
| Coding Plan 厂商条款限制共享 | 封号、限流或合规风险 | 默认 grant_only；录入前确认条款；优先使用官方 API |
| 审计正文包含敏感数据 | 数据泄露 | 安全脱敏、管理端管理员专属正文、读取操作审计、数据库与备份访问控制 |
| 审计数据持续增长 | 存储压力与查询下降 | 单条容量上限、索引治理、归档和对象存储 |
| 上游协议与错误语义差异 | 兼容性和可用性下降 | 官方协议直通、模板化适配、连接测试、确定性错误契约 |
| 渠道配置或授权实时变化 | 已签发 Key 暂时不可用 | 每次请求复核，返回稳定错误，管理端提供状态与审计定位 |
| 渠道隔离回归 | 请求命中错误采购渠道 | 全协议隔离矩阵、同名模型测试、重试与亲和测试 |
| 单节点故障 | 服务中断 | 健康检查、数据库备份和生产加固计划 |

### 15.2 外部依赖

- 公司合法采购且允许相关使用方式的官方服务凭证；
- 内网至官方模型 API 的稳定出网能力；
- PostgreSQL、Redis、域名、TLS 证书和备份运维能力；
- 信息安全和合规团队对审计正文范围、保留期限与 Coding Plan 使用方式的确认。

## 17. 术语与相关文档

### 17.1 术语表

| 术语 | 含义 |
|---|---|
| Provider | 上游模型供应商 |
| ProductLine / 上游渠道 | 同一供应商下独立配置、授权和调度的 API 或 Coding Plan 产品线 |
| UpstreamCredential | 上游官方 API Key 或套餐访问凭证 |
| 员工 API Key | TokenHub 签发给员工的内部调用令牌 |
| 兼容协议 | `openai_chat`、`openai_responses` 或 `anthropic_messages` |
| 硬绑定 | 一把员工 Key 的模型、凭证、重试和亲和范围固定在一个 ProductLine |
| public_pool | 对 active 员工开放渠道内符合条件凭证的共享模式 |
| grant_only | 只向被授权员工开放指定凭证的共享模式 |
| 软上限 | 超额后继续放行并记录标记 |
| 硬上限 | 超额后拒绝请求 |
| 审计正文 | 经过安全脱敏并受容量上限约束的请求和响应内容 |
