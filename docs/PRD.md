## 1. 背景与问题

### 1.1 现状

公司采购并分配了多份官方大模型服务凭证（典型为智谱等），按员工一人一 Key 使用。实际出现：

- **额度不均**：部分员工额度不够用，部分员工额度长期闲置  
- **管理分散**：Key 散落在个人环境，难统一治理、难审计  
- **不可观测**：无法系统回答「谁用了多少 Token、提示了什么、模型回了什么」  

市面常见「中转站 / New API」类产品能力完整，但重心在 **对外售卖、多租户计费、渠道聚合转售**，与公司内网、共享官方额度、强制全文审计的诉求 **并不完全匹配**。

### 1.2 机会

建设公司内网统一出口 **TokenHub**：

1. 将官方 API（及受控的 Coding Plan）纳入 **共享池**，提高采购利用率  
2. 员工只持 **内部身份 + 内部 API Key**，不再直持上游 Key  
3. 对每次调用做 **全文审计与用量统计**（不计费）  
4. 为后续扩展多官方供应商（智谱国内/国际、MiniMax、Kimi、DeepSeek 等）预留架构  

---

## 2. 产品定位

> **TokenHub = 公司内网 LLM 统一网关 + 官方凭证池调度 + 员工级全量调用审计（不计费）**

一句话：

- **不是** 对外 API 转售平台  
- **不是** 再造完整 New API 商业中转站  
- **是** 企业内网的「官方模型出口 + 共享池 + 审计台账」  

### 2.1 成功标准（一期验收导向）

| 指标 | 目标 |
|---|---|
| 共享 | 多个官方 API Key 可被全员（或授权范围）共享使用，避免一人一池割裂 |
| 接入成本 | 员工仅改 Base URL + 使用内部 API Key 即可调用（OpenAI 兼容） |
| 审计 | 每次请求可追溯：人、时间、模型、供应商、Token、完整 prompt/response |
| 管控 | 支持软日上限告警 + RPM/并发；可选硬上限 |
| 角色 | 管理员只做管理；员工只做自助；禁止自助注册 |
| 部署 | 内网可部署；开发环境对接独立 Postgres / Redis |

## 3. 目标与非目标

### 3.1 目标（Goals）

1. **凭证池化**：上游官方 Key/套餐凭证集中托管，网关按策略选用  
2. **全员共享 API 额度**（默认）；Coding Plan 默认谨慎授权  
3. **不计费**：不做充值、套餐售卖、余额账户；只做用量与审计  
4. **全文永久审计**：提示词、返回内容尽量完整落库，长期保留  
5. **身份可控**：姓名 + 手机号 + 初始密码；管理员批量建号；首次强制改密  
6. **多官方供应商可扩展**：智谱国内/国际、MiniMax、Kimi、DeepSeek 等  
7. **双端产品**：管理后台 + 员工自助页（角色隔离，管理员不进员工端）  

### 3.2 非目标（Non-Goals）

| 明确不做（一期及默认长期） | 说明 |
|---|---|
| 对外公开注册 / 售卖 API | 仅公司内部 |
| 预扣费、退款、倍率计费、支付对接 | 与定位冲突 |
| 仿 New API 的 40+ 供应商全家桶 | 只接公司实际采购的官方服务 |
| 员工自助注册 | 仅管理员建号 |
| 网页 Chat Playground（一期） | 调用走 IDE/脚本 `/v1`；二期可选 |
| 替代公司 SSO（一期） | 二期可对接企微/OIDC |

## 4. 用户与角色

| 角色 | 入口 | 职责 |
|---|---|---|
| **管理员 (admin)** | 仅 `/admin/*` | 批量建号、停用账号、渠道/凭证、模型目录、配额策略、全员审计、日志授权、看板 |
| **审计员 (auditor)** | 仅 `/admin/*`（能力子集） | 在授权范围内查阅调用日志与统计；无建号/改渠道等写权限（可随实现细化） |
| **员工 (employee)** | 仅 `/me/*` | 登录改密、管理自己的 API Key、查看自己的用量与调用记录 |
| **调用方（机器）** | `POST /v1/*` | 使用员工 API Key 调模型；无页面 |

### 4.1 角色隔离原则

- **管理员就是管理员**：登录后只进入管理后台，**不进入员工页面**  
- **员工不能进入管理后台**  
- 无「返回员工端 / 进入管理端」的交叉导航（避免身份混淆）  

### 4.2 账号规则

| 规则 | 说明 |
|---|---|
| 标识 | 手机号唯一登录 |
| 建号字段 | 姓名、手机号、初始密码、部门（可选）、角色 |
| 注册 | **禁止**员工自助注册 |
| 批量 | 支持批量导入建号 |
| 首次登录 | `must_change_password = true`，强制改密后才能使用业务功能 |
| 调用凭证 | 员工 API Key（`th_...`）；哈希用于鉴权，加密托管副本仅供管理员审计后复制 |
| 上游凭证 | 仅管理员维护；加密存储；界面仅显示末几位 |

## 5. 核心场景

### 5.1 管理员开户

1. 管理员登录管理后台  
2. 单个创建或批量导入员工  
3. 员工使用手机号 + 初始密码登录 → 强制改密  
4. 员工在自助页生成 API Key  

### 5.2 员工调用模型

1. 在 IDE/脚本配置：  
   - `base_url = https://tokenhub.公司内网/v1`  
   - `api_key = th_xxx`  
2. 发起 `chat/completions`  
3. 网关：鉴权 → 限流/配额检查 → 选上游凭证 → 转发 → 记录审计与用量  
4. 员工可在「我的调用」查看记录与正文（默认可看自己的全文）  

### 5.3 额度共享

- 多个官方 **API** Key 进入公共池  
- 调度按优先级/权重/健康度选用；失败按策略换 Key 重试  
- 员工无感知具体使用了哪把上游 Key（审计侧记录 credential 标识/末四位）  

### 5.4 审计与授权查阅

- 每次调用：元数据 + 完整 request/response 永久保存  
- 管理员默认可查全员全文  
- 可通过 **日志查阅授权** 授予审计员/他人：范围（全员/部门/指定人）、是否含正文、有效期  
- 查看他人正文写入 **操作审计**  

### 5.5 Coding Plan（与 API 区分）

- 产品线标记为 `coding_plan`  
- 默认 **grant_only**（授权制），**不参与**自动混部  
- 重试策略更保守，避免多号连刷触发官方风控  
- 计量可能不完整：报表以请求次数 + 可用 tokens 双轨，并标注计量来源

### 6.2 页面信息架构

#### 员工端 `/me`

- 工作台：今日/本月用量、接入说明（Base URL、Header 示例）  
- API Key：生成、吊销  
- 我的调用：列表与详情（全文）  

#### 管理端 `/admin`

- 概览：人数、凭证数、今日请求/Token  
- 员工管理：搜索、新建、批量导入、启停、复制员工 API Key
- （P1+）上游渠道、日志中心、授权、配额策略、操作审计

### 6.3 关键 API 域

| 域 | 前缀 | 鉴权 |
|---|---|---|
| 健康 | `/health` | 无 |
| 认证 | `/api/auth/*` | 登录无；其余 Session/JWT |
| 员工自助 | `/api/me/*` | 员工 JWT + 已改密 |
| 管理 | `/api/admin/*` | 管理员/审计员 JWT + 已改密 |
| 模型代理 | `/v1/*` | 员工 API Key |

`/v1` 原生支持 Chat Completions、Responses（含 `/responses/compact`）与 Anthropic Messages。协议绑定 Key 只能调用对应入口，不进行跨协议转换。

## 7. 渠道与调度策略

### 7.1 概念模型

```text
Provider（供应商）
  └─ ProductLine（产品线：api | coding_plan）
        └─ UpstreamCredential（具体 Key/套餐凭证，可同时声明多个原生协议）
ModelRoute：client_model → product_line + upstream_model
EmployeeApiKey：员工内部 Key → 唯一传输协议
```

### 7.2 共享策略默认值

| product_type | share_mode 默认 | 自动选路 | 说明 |
|---|---|---|---|
| api | public_pool | 是 | 全员共享额度主路径 |
| coding_plan | grant_only | 否 | 授权制；合规与风控优先 |

### 7.3 调度算法（借鉴 New API 思路，简化实现）

1. 根据员工 Key 确定唯一传输协议
2. 根据 `model` 查 `model_routes` 得候选产品线
3. 过滤：渠道声明支持该协议、启用中、员工有权（公共池或授权）、凭证未冷却/未自动禁用
4. 按 **priority 降序**；同优先级 **weight 加权随机**（或轮询）
5. 失败按状态码决定是否换凭证重试

### 7.4 错误处理建议

| 上游信号 | 动作 |
|---|---|
| 401 / 403（鉴权失败） | 凭证 auto_disabled；API 池可换下一个 |
| 429 | 短冷却（如 30–60s）；换下一个 |
| 5xx / 网络错误 | 换下一个，最多 N 次（默认 2） |
| 400 参数错误 | 不换凭证，直接返回客户端 |
| Coding 风控/套餐错误 | 少重试、记审计、告警 |

### 7.5 配额治理（不计费）

| 策略 | 默认建议 | 行为 |
|---|---|---|
| 员工日 Token 软上限 | 如 200 万/人/日（可配） | 超限仍放行 + 告警标记 |
| 员工日 Token 硬上限 | 默认关 | 打开后超限拒绝 |
| RPM | 60/人/分钟 | 超限拒绝 |
| 并发 | 5/人 | 超限拒绝 |
| 日请求软/硬上限 | 可选 | 对 Coding 类更友好 |

## 8. 审计与合规

### 8.1 必须记录的信息

**元数据（request_audits）**  
员工、API Key id、传输协议、时间、client/upstream 模型、provider、product_type、凭证 id/末四位、流式与否、状态、HTTP 状态、错误码、token 用量、usage 原始 JSON、耗时、重试轨迹、IP、UA、路径等。

**正文（request_audit_bodies）**  
完整 request body（含 messages 等）、完整 response（流式需拼接）、可选脱敏后的 headers；过大可外置。

### 8.2 保留策略

- **永久保留**（不做自动删除）  
- 磁盘压力时采用 **归档迁移**，不改变「业务上可查」的产品承诺（归档介质与检索方式另案）  

### 8.3 可见性

| 主体 | 元数据 | 全文 |
|---|---|---|
| 员工 | 仅自己 | 默认可以（系统配置可关） |
| 授权审计员 | 授权范围 | 视 `can_read_body` |
| 管理员 | 全部 | 全部 |

### 8.4 安全要求

- 上游 Secret：AES 等加密存储 + 独立 `CREDENTIAL_ENCRYPT_KEY`  
- 员工 API Key：哈希用于鉴权；可逆托管副本按独立用途域加密；仅管理员可读取并审计
- 传输：内网 HTTPS（生产）  
- 管理操作与「查看他人对话」必须操作审计  
- 明确：经 TokenHub 出网至官方模型服务的数据范围需符合公司合规制度  

### 8.5 与 Coding Plan 相关的合规提示

多账号/多终端共享 **Coding Plan** 可能违反厂商条款或触发风控。产品默认 **授权制、不自动混部**；开启公共调度需管理员显式确认风险。

## 9. 系统架构

### 9.1 逻辑架构

```text
员工 IDE/脚本 ──API Key──► TokenHub API ──► 官方上游（智谱/DS/Kimi/MiniMax…）
管理员/员工浏览器 ──JWT──► TokenHub Web ──► TokenHub API
                              │
                     PostgreSQL + Redis
```

### 9.2 技术栈（已定）

| 层 | 选型 |
|---|---|
| 前端 | Vue 3 + TypeScript + Vite + Element Plus + Pinia + Vue Router |
| 后端 | Node.js + TypeScript + Fastify |
| ORM | Drizzle |
| 主库 | PostgreSQL 16 |
| 缓存 | Redis 7（会话辅助、限流、冷却） |
| 包管理 | pnpm workspace |

### 9.3 基础设施约定（开发）

- 使用本机 **Colima 独立数据库服务**（与 New API 容器隔离）  
- PostgreSQL：`127.0.0.1:5432`，业务库建议 **`tokenhub`**  
- Redis：`127.0.0.1:6379`，建议 **db index = 1** 或 key 前缀 `th:`  
- 密码仅存在本地 `.env`（权限 600），不进 Git、不进聊天记录  
- API 开发默认端口 **3100**（避免与本机 3000 冲突）；Web **5173**  

### 9.4 与 New API 的关系

| 可借鉴 | 不照搬 |
|---|---|
| 渠道 priority/weight、失败重试、限流、Body 可重读、OpenAI 兼容代理 | 预扣费/退款/倍率/充值 |
| MultiKey / 凭证健康、状态码策略 | 多租户售卖、海量供应商 |
| 日志用户/管理员字段剥离思路 | 仅用量摘要、无全文对话审计 |
| Go 分层思想（映射到 Node 模块） | AGPL 整仓 fork 作为公司闭源产品（需法务评估；本项目 **自研**） |

定位：**New API 的企业内网子集 + 审计超集**。

## 10. 数据模型（逻辑）

### 10.1 核心实体

| 实体 | 说明 |
|---|---|
| employees | 员工账号 |
| employee_api_keys | 内部调用 Key |
| providers / product_lines / upstream_credentials | 上游三维渠道 |
| credential_employee_grants | Coding 等授权 |
| model_routes | 模型路由 |
| quota_policies / employee_quota_overrides | 配额策略 |
| usage_counters_daily | 人日用量 |
| request_audits / request_audit_bodies | 审计元数据 + 全文 |
| log_access_grants | 日志查阅授权 |
| ops_audit_logs | 管理操作审计 |
| system_settings | 系统开关 |

### 10.2 种子与空库策略

- **仅种子用户**：管理员账号（`SEED_ADMIN_*`），禁止预置演示业务数据
- **不预置**上游渠道和调用日志
- 默认配额策略：`default`（系统运行所需最小配置，非演示数据）
- 上游渠道由管理员按实际采购的 API Key 录入，内部供应商与产品线自动配置

| 性能 | 流式转发低缓冲延迟；审计写入可异步优化（一致性策略实现期定） |
| 存储 | 全文永久；预估按调用量扩容；可选对象存储 |
| 安全 | 密钥分层、权限分离、操作审计 |
| 可运维 | 环境变量配置、迁移脚本、种子与管理员重置脚本 |
| 国际化 | 一期中文界面即可 |

### 12.2 当前已实现能力

**M1 骨架**

- 登录 / 强制改密 / 角色路由隔离（管理员不进员工端）  
- 员工：工作台、API Key、调用列表壳  
- Postgres 全量表结构；种子仅管理员 + 默认配额（无演示供应商/凭证）
- `/health`、Redis 连通  

**M2 代理闭环**

- 员工 API Key 鉴权且每个 Key 绑定唯一协议；`GET /v1/models`、`POST /v1/chat/completions`、`POST /v1/responses`、`POST /v1/responses/compact`、`POST /v1/messages` 与 `POST /v1/messages/count_tokens` 已启用
- 管理员可在员工列表复制员工 API Key；旧版仅哈希 Key 会引导生成新的托管 Key，读取响应禁止缓存并写入操作审计
- 显式模型路由与已发现模型自动路由；按授权、状态、优先级和权重筛选凭证
- 默认最多三次候选尝试且不重复 Key：`401/403` 自动停用、`429` 冷却、`5xx`/网络错误切换，参数 `400` 不重试
- Chat、Responses、Messages 均按原生请求/响应格式直通；非流式 JSON 与 SSE 字节流转发，首字节后不重试，客户端断开会取消上游
- Responses 以 `response.completed/failed/incomplete/error`、Messages 以 `message_stop/error` 判定流终态；工具调用与增量参数保持原生事件
- Redis RPM/并发租约、日软硬配额与当地日期用量累计
- 请求/响应正文、流式拼装结果、usage、重试轨迹与成功/错误/取消终态写入审计；Authorization 不入库

**M3 管理后台（完整管理能力）**

- 概览：今日请求/Token/失败、Top 员工、按供应商、最近错误  
- 员工管理：新建 / 批量导入 / 启停  
- 上游渠道：按供应商与产品线分组，一个渠道可批量录入和管理多条加密 API Key；支持连接测试、模型发现、批量测试/启停/删除，渠道内可用 Key 等权调度
- 供应商、产品线和模型路由作为内部结构，由上游渠道自动配置，不提供独立管理页面
- 调用日志：检索、详情、按需加载全文（写操作审计）  
- 日志查阅授权：范围 all/dept/employees、正文权限、撤销  
- 配额策略与员工覆盖  
- 操作审计列表  

**M2 验证记录（2026-08-04）**

- 本地隔离 Mock：`401 → 换 Key`、`400 不重试`、`429 → 冷却并换 Key`、`500 → 首字节前切换 SSE` 均通过
- 本地原生协议 Mock：Responses JSON/SSE/compact、Messages JSON/SSE、模型隔离、协议绑定 Key、Bearer/x-api-key、版本/Beta 头透传、usage 与审计均通过
- DeepSeek：非流式与流式真实调用均为 HTTP 200，流式包含 `[DONE]`，usage 与审计一致
- GLM：模型目录连通；Chat Completions 返回供应商业务码 `1113`（余额不足或无可用资源包），待渠道充值后复测
