# TokenHub v0.0.4 规划

| 项 | 内容 |
|---|---|
| 版本 | `v0.0.4` |
| 基线 | `2179b58`（v0.0.3） |
| 状态 | **已实施** |
| 目标 | 修正管理首页渠道统计；将权限模型彻底收敛为员工、管理员两种角色；操作审计列表分页每页 10 条 |

## 1. 版本范围与边界

本版本包含三项 P0 改动：

1. `/admin` 首页的渠道指标按渠道聚合，不再把 Key 数量显示成渠道数量。
2. 权限只保留员工与管理员，完整移除第三种只读管理角色以及为它服务的日志授权体系。
3. `/admin/ops-audit` 操作审计列表采用分页，**每页 10 条**，与调用日志列表口径一致。

项目尚未部署，本版本按“干净基线”处理：不提供旧角色映射、不保留旧接口、不返回 `deprecated` 或 HTTP 410、不编写过渡迁移，也不保留仅用于兼容旧实现的类型、分支、注释和测试。

### 1.1 “审计”一词的范围

本规划将需求中的“没有审计”解释为：**不再存在独立的审计权限角色**。以下业务能力不是权限角色，继续保留并改为管理员专属：

- 调用日志与已脱敏的请求上下文；
- 管理员操作记录；
- `request_audits`、`request_audit_bodies`、`ops_audit_logs` 等运行记录。

需要删除的是第三角色、日志范围授权、只读管理入口以及所有相关判断。如果目标是连调用日志和管理员操作记录也一并删除，那将是另一项影响排障、安全和用量统计的数据模型变更，不在本规划内。

### 1.2 “不留痕迹”的落地标准

实施完成后，当前产品基线中只描述员工与管理员：

- 运行时代码、类型、数据库结构、迁移快照、测试和界面中不存在第三角色；
- 不存在日志授权表、授权范围枚举、授权 API、授权页面或授权判断；
- 不存在兼容接口、迁移映射、废弃提示或“曾支持第三角色”的代码注释；
- README、PRD 和 v0.0.1～v0.0.3 的产品基线同步改为双角色，不让旧规划继续成为错误实现依据；
- 本文作为 v0.0.4 的变更说明保留。Git 历史是否压缩或改写不属于产品实现，除非另行明确要求。

## 2. 管理首页渠道统计修复

### 2.1 根因

当前 `GET /api/admin/overview` 从 `upstream_credentials` 直接统计：

- Key 总数；
- 状态为 `active` 的 Key 数；
- 状态为 `auto_disabled` 的 Key 数。

接口把这组数据返回为 `credentials`，而 `DashboardView.vue` 分别显示为“共 N 个渠道”“启用渠道”和“异常渠道”。因此一个渠道配置四个 Key 时，首页会错误显示四个渠道。

TokenHub 当前的渠道实体是 `product_lines`，供应商实体是 `providers`，Key 实体是 `upstream_credentials`。首页所有渠道指标必须以 `product_lines.id` 为唯一聚合单位。

### 2.2 指标口径

概览接口改为返回：

```json
{
  "success": true,
  "data": {
    "channels": {
      "total": 1,
      "enabled": 1,
      "unavailable": 0
    }
  }
}
```

字段定义写死如下：

- `total`：`product_lines` 总数；一个产品线只算一个渠道，与 Key 数量无关。
- `enabled`：供应商状态和产品线状态均为 `active` 的渠道数；这是配置启用状态，包括暂时没有可调度 Key 的渠道。
- `unavailable`：在 `enabled` 渠道中，可调度 Key 数为 0 的渠道数。
- 可调度 Key：复用现有 `effectiveCredentialStatus(status, coolUntil, now)` 口径，生效状态为 `active` 且 `weight > 0`。
- 只要渠道还有至少一个可调度 Key，其他 Key 处于冷却、停用或自动停用状态都不会把整个渠道计为异常。
- 供应商或产品线主动停用时，该渠道计入 `total`，不计入 `enabled` 和 `unavailable`。
- 已启用但尚未配置任何 Key 的渠道计入 `unavailable`。

`enabled` 和 `unavailable` 可以重叠：后者表示“配置已启用，但当前无法调度”。前端异常卡片说明改为“已启用但暂无可调度 Key”，不再显示“自动停用”，避免把 Key 状态误写成渠道状态。

### 2.3 服务端实现

修改 `server/src/routes/admin/overview.ts`：

1. 删除按 `upstream_credentials` 分别执行三个 `count()` 的实现。
2. 一次查询读取产品线、供应商状态及 Key 的状态、`coolUntil`、`weight`，用 `productLineId` 聚合；必须使用左连接，确保无 Key 渠道不会消失。
3. 抽取可单测的渠道汇总函数，复用渠道详情接口现有的有效状态定义，避免首页与 `/api/admin/product-lines/:id/summary` 出现两套口径。
4. 响应删除 `credentials`，只返回 `channels`；项目未上线，不做双字段兼容。
5. `/api/admin/overview` 收敛为管理员专属。

聚合必须是常数次数据库查询，禁止为每个渠道单独查询 Key。所有状态计算共用同一个 `now`，避免冷却刚过期时同一响应中出现不一致。

### 2.4 前端实现

修改 `web/src/views/admin/DashboardView.vue`：

- 响应类型由 `credentials` 改为 `channels`；
- “启用渠道”读取 `channels.enabled`；
- “共 N 个渠道”读取 `channels.total`；
- “异常渠道”读取 `channels.unavailable`；
- 异常高亮仅由 `unavailable > 0` 决定；
- 删除仅为只读管理角色存在的按钮、说明和分支。

“接入平台”继续统计 `providers`，不与渠道数合并；“启用路由”继续统计启用的 `model_routes`，本版不改变这两个指标。

### 2.5 自动化验收矩阵

| 数据场景 | `total` | `enabled` | `unavailable` |
|---|---:|---:|---:|
| 1 个启用渠道，4 个 Key，至少 1 个可调度 | 1 | 1 | 0 |
| 1 个启用渠道，4 个 Key 全部不可调度 | 1 | 1 | 1 |
| 1 个启用渠道，没有 Key | 1 | 1 | 1 |
| 1 个主动停用渠道 | 1 | 0 | 0 |
| 供应商停用、产品线启用 | 1 | 0 | 0 |
| 2 个渠道共 10 个 Key，均有可调度 Key | 2 | 2 | 0 |
| 1 个 Key 自动停用、另 1 个 Key 可调度 | 1 | 1 | 0 |
| 冷却已到期且权重大于 0 的 Key | 1 | 1 | 0 |

重点回归用户报告的现场：数据库只有一个 `product_lines` 记录、存在四个 `upstream_credentials` 记录时，首页必须显示“共 1 个渠道”。

## 3. 权限模型收敛为双角色

### 3.1 最终权限矩阵

| 角色 | Web 入口 | API 能力 |
|---|---|---|
| 员工 `employee` | `/me/*` | 管理自己的调用 Key、查看自己的调用记录和用量、调用代理接口 |
| 管理员 `admin` | `/admin/*` | 员工、渠道、路由、配额、全量调用日志和管理员操作记录 |

边界继续保持：

- 员工不能访问 `/api/admin/*`；
- 管理员不能进入员工端，也不能创建或读取员工调用 Key 明文；
- 员工变更为管理员时，在同一事务中吊销其全部 active 调用 Key；
- 管理员变更为员工时，不恢复历史已吊销 Key；
- 所有管理端接口只接受 `admin`，不再有“只读管理端”权限子集。

### 3.2 数据库与迁移

数据库最终结构只保留：

```text
employee_role = ('employee', 'admin')
```

完整删除：

- `grant_scope` 枚举；
- `log_access_grants` 表、索引、外键和 Drizzle schema 导出；
- 仅用于日志范围授权的种子、清理脚本和目标解析逻辑。

由于项目没有部署，不新增“先迁移旧角色、再删除枚举值”的兼容迁移。实施方式为：

1. 先完成最终 schema 修改；
2. 将现有开发期迁移整理为一份可从空库直接得到最终结构的干净基线；
3. 重新生成 Drizzle journal 和 snapshot，基线中从未创建第三角色、授权枚举或授权表；
4. 重建本地开发数据库，再执行 seed；seed 只创建管理员和员工数据；
5. 从空数据库执行完整迁移与测试，确保没有依赖被删除对象。

重建数据库会删除本地开发数据。实施前先确认数据可丢弃；如需保留业务测试数据，只导出仍属于最终 schema 的数据后再导入，不导出旧角色和授权记录。

### 3.3 服务端清理

服务端需要完成以下清理：

- `employeeRoleEnum`、JWT/Session 类型和 Zod 校验只允许 `employee | admin`；
- 登录、鉴权中间件和当前用户响应不再识别第三角色；不做静默降级或角色映射；
- `POST/PATCH /api/admin/users` 的角色字段只接受员工和管理员；
- 概览、供应商、产品线、Key、模型路由、调用日志和管理员操作记录接口全部改为管理员专属；
- 删除 `server/src/routes/admin/grants.ts`，并从 `server/src/app.ts` 移除注册；`/api/admin/log-grants` 应像从未存在一样不注册，而不是返回废弃提示；
- 删除 `server/src/lib/log-access.ts` 以及调用日志中的授权范围查询；管理员直接按请求筛选条件读取全量日志；
- 删除操作记录中 `log_access_grant` 目标的批量解析和相关 action 文案；
- 删除 demo 清理脚本、测试夹具、注释中与第三角色或日志授权相关的分支；
- 保留管理员读取上下文时的 `log.read_context` 记录及 5 分钟去重，它属于管理员操作记录，不属于角色授权。

鉴权载荷必须做运行时角色校验，不能用 TypeScript 强制转换把数据库或 JWT 中的任意字符串当成合法角色。非法角色载荷直接判定为未授权。

### 3.4 前端清理

前端需要完整删除：

- `web/src/views/admin/LogGrantsView.vue`；
- `/admin/log-grants` 路由、侧边栏入口和页面跳转；
- auth store、路由 meta、登录重定向和主页选择中的第三角色类型与判断；
- `isAuditor`、只读管理视角及其派生 computed；
- 员工创建/编辑表单中的第三角色选项；
- 用户详情、个人中心和操作记录字典中的第三角色标签；
- 渠道、日志、概览页面中仅用于区分管理员与只读角色的按钮和提示。

管理端路由守卫统一只允许管理员。员工登录后只进入 `/me`，管理员登录后只进入 `/admin`；不存在第三种重定向路径或兜底页面。

### 3.5 文档清理

同步修改以下产品基线：

- `README.md`；
- `docs/PRD.md`；
- `docs/v0.0.1.md`、`docs/v0.0.2.md`、`docs/v0.0.3.md`；
- `docs/v0.0.3-review.md`。

文档中的权限矩阵、路由说明、正文可见性、测试要求和架构图全部改为双角色。调用日志和管理员操作记录可以继续使用“记录”“日志”等业务名称，但不能再描述第三角色、日志授权范围或只读管理入口。

## 4. 操作审计分页

管理端 `OpsAuditView`（`/admin/ops-audit`）列表分页写死如下：

- 每页固定 **10** 条（与 `/admin/logs` 一致），不再使用 50 条。
- 请求参数：`limit=10`，`offset = (page - 1) * 10`。
- 分页组件展示总数、上一页/页码/下一页；切换页码重新请求 `GET /api/admin/ops-audit`。
- 点击「查询」或变更筛选条件时重置为第 1 页再加载。
- 接口已支持 `limit`/`offset`/`total`，本版只调整前端默认页大小与分页行为，不改服务端契约。

## 5. 测试计划

### 5.1 单元测试

- 渠道汇总函数覆盖 §2.5 的全部矩阵；
- 冷却过期、`weight = 0`、无 Key、供应商停用和产品线停用边界；
- 权限类型只包含员工与管理员；
- 员工升为管理员时 Key 吊销逻辑继续通过；
- 管理员上下文读取去重逻辑继续通过。

### 5.2 API 集成测试

- 一个渠道配置四个 Key，`GET /api/admin/overview` 返回 `channels.total = 1`；
- 响应不存在旧的 `credentials` 渠道统计字段；
- 管理员可以访问所有 `/api/admin/*` 现存接口；
- 员工访问任一管理接口返回 403；
- `/api/admin/log-grants` 未注册，返回 404；
- 管理员可查看全量日志和上下文，员工只能通过 `/api/me` 查看自己的记录；
- 从空数据库执行迁移和 seed 成功，schema 中不存在被删除的枚举和表。

### 5.3 前端与构建验证

```bash
npm run build
npm run test:server
npm run db:setup
```

另执行一次全仓检索。除本文这份变更说明外，运行时代码、测试、迁移和产品基线中不得再出现第三角色标识、日志授权表名、日志授权 API 或相应中文角色名称。检索结果必须逐项人工确认，不能仅靠改写大小写绕过。

### 5.4 手动验收

1. 重建并 seed 本地数据库，使用管理员登录 `http://localhost:5174/admin`。
2. 创建或保留一个渠道，给它配置四个 Key，刷新首页；确认显示“共 1 个渠道”。
3. 逐一停用四个 Key，刷新首页；确认“启用渠道”为 1、“异常渠道”为 1。
4. 重新启用任意一个权重大于 0 的 Key，刷新首页；确认“异常渠道”恢复为 0。
5. 停用产品线或供应商；确认渠道仍计入总数，但不计入启用和异常。
6. 打开员工管理，新建与编辑表单只能选择员工、管理员。
7. 检查管理端侧边栏和前端路由，不存在日志授权入口。
8. 管理员打开调用日志、上下文和管理员操作记录，确认功能正常。
9. 打开 `/admin/ops-audit`：确认每页最多 10 条、底部分页可用；总数超过 10 时可翻页；筛选查询后回到第 1 页。
10. 使用员工账号访问 `/admin` 和管理 API，确认分别重定向/返回 403；员工端个人用量和调用记录正常。

## 6. 实施顺序

1. 增加渠道聚合单元测试，修复 overview 接口与首页字段。
2. 收敛服务端角色类型和所有管理 API，删除日志授权实现。
3. 收敛前端权限、路由和页面，删除日志授权界面。
4. 操作审计列表分页改为每页 10 条。
5. 清理 schema、seed、demo 脚本和测试夹具，生成干净迁移基线。
6. 重建本地数据库，执行空库迁移、seed、自动化测试和手动验收。
7. 同步 README、PRD、历史版本基线和版本号到 `0.0.4`。
8. 执行全仓残留检索与最终构建，通过后再提交。

## 7. 完成定义

v0.0.4 只有同时满足以下条件才算完成：

- 一个渠道无论配置多少 Key，首页渠道总数始终为 1；
- 渠道异常状态按“启用但无可调度 Key”聚合，绝不按异常 Key 条数显示；
- 产品只存在员工、管理员两种权限角色；
- 日志授权数据结构、接口、页面和判断全部消失，没有兼容层；
- 调用日志与管理员操作记录仍由管理员正常使用；
- 操作审计列表每页 10 条，分页与筛选重置逻辑正确；
- 干净空库可以一次迁移到最终 schema；
- 服务端测试、前后端构建、手动验收和残留检索全部通过；
- 根目录、Server、Web 版本号和锁文件统一为 `0.0.4`。
