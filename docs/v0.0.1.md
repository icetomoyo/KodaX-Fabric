## 2. 修改功能

### 2.1 功能名称

**员工 API Key 创建流程：先选上游渠道，再选兼容协议**

### 2.2 背景与问题

#### 现状（修改前）

员工在 `/me/keys` 创建 API Key 时：

1. 只需填写 **名称**
2. 从全局固定的 3 种协议中任选一种：
   - `openai_chat`（OpenAI 对话 / Chat Completions）
   - `openai_responses`（OpenAI Responses）
   - `anthropic_messages`（Anthropic Messages）
3. **不选择**、也 **不感知** 上游渠道（Provider / ProductLine）
4. 数据模型 `employee_api_keys` 仅绑定 `protocol`，**无渠道字段**
5. 实际请求时，由网关根据 `model` → `model_routes` + 公共池/授权规则 **自动** 选上游凭证

#### 问题

1. 员工容易选到 **与目标上游渠道不兼容** 的协议（例如渠道只声明了 `openai_chat`，却创建了 `anthropic_messages` Key）
2. 创建时无法表达「这把 Key 是为某条上游渠道准备的」，后续排查与接入说明不直观
3. 管理端上游凭证已具备 **凭证级协议声明**（`upstream_credentials.supported_protocols`），员工端创建却未聚合并复用该约束

### 2.3 目标行为（修改后）

员工创建 API Key 必须按以下顺序完成：

```text
1) 选择上游渠道（产品线 / ProductLine）
2) 在该渠道「兼容协议」集合中选择一种传输协议
3) 填写名称并创建
```

创建成功后：

- 该 Key **绑定** 所选上游渠道 + 所选协议
- 列表与详情展示渠道信息与协议
- 使用该 Key 发起 `/v1/*` 请求时，模型发现与请求调度均 **限制在绑定渠道内**（硬绑定，见 2.9）

### 2.4 名词与范围

| 名词 | 含义 | 对应数据 |
|---|---|---|
| 上游渠道 | 员工可见的业务渠道，对应「供应商下的一条产品线」 | `product_lines` + `providers` |
| 兼容协议 | 该渠道下至少有一把凭证声明支持的传输协议并集；创建时仅允许从中选择 | 渠道内 `upstream_credentials.supported_protocols` 聚合结果 |
| 员工 API Key | 员工侧调用 TokenHub 的凭证 | `employee_api_keys` |
| 硬绑定 | Key 只能走创建时选定的渠道，失败时仅在该渠道内换凭证，不跨渠道 | 调度约束 |

**不在本版本范围：**

- 不改变管理端「上游渠道」的增删改与 Key 池管理交互
- 不实现上游余额/额度统计
- 不改员工端登录、改密、配额策略页面
- 不引入「创建时绑定到某一把具体上游 secret」（只绑到渠道 / 产品线，不绑单把 Key）

### 2.5 员工端交互详细说明

#### 2.5.1 入口

- 页面：`http://{host}/me/keys`
- 操作：点击 **创建 Key**

#### 2.5.2 创建弹窗字段（顺序固定）

| 顺序 | 字段 | 控件 | 必填 | 说明 |
|---|---|---|---|---|
| 1 | 上游渠道 | 单选列表 / 下拉 | 是 | 展示员工 **有权使用** 的渠道；未选渠道时，协议不可选 |
| 2 | 兼容协议 | 单选 | 是 | 选项 **动态来自** 所选渠道的兼容协议；渠道变更后重置协议 |
| 3 | 名称 | 文本 | 是 | 1–100 字；沿用现逻辑（如「本机 Cursor」） |

**渠道选项展示建议字段：**

- 供应商名称 / 短名（如 GLM、DeepSeek）
- 渠道名称（产品线 name）
- 可选：产品类型（`api` / `coding_plan`）、共享模式文案
- 不展示上游 `baseUrl`：员工调用始终使用 TokenHub Base URL，避免混淆和暴露内部上游地址

**协议选项展示建议字段：**

- 短名（如「OpenAI 对话」）
- 端点提示（如 `POST /v1/chat/completions`）
- 鉴权头提示（沿用现有 `relay-protocol` 文案）

#### 2.5.3 交互规则

1. **打开弹窗**
   - 清空表单
   - 拉取「可选上游渠道」列表
   - 若列表为空：显示空态说明（例如「暂无可用上游渠道，请联系管理员配置」），禁用创建按钮
2. **选择渠道后**
   - 加载/展示该渠道 `compatibleProtocols`
   - 协议按服务端固定顺序返回：`openai_chat` → `openai_responses` → `anthropic_messages`
   - 只要协议列表非空，默认选中第一个，以减少操作并保证前后端行为确定
   - 若协议列表为空：提示「该渠道未声明可用协议」，禁用创建
3. **切换渠道**
   - 按新渠道重新计算协议选项，并选中其第一个协议
   - 不得保留上一渠道的协议值（避免提交非法组合）
4. **提交**
   - 前端校验：渠道、协议、名称均已填写
   - 后端再次校验：员工对该渠道有权、协议属于该渠道兼容集
   - 成功：仅在创建响应中返回明文 Key，并进入「仅展示一次」结果态
   - 结果态必须直接显示完整 Key、提供复制按钮，并提示「关闭后员工无法再次查看」；不能只依赖自动写入剪贴板
   - 员工确认已保存后方可关闭结果态
5. **列表**
   - 增加「上游渠道」列（供应商 · 渠道名）
   - 保留「协议」列
   - 员工仅可删除 Key，不提供创建后的再次揭示/复制能力
   - 管理员按总 PRD 保留审计后的 reveal/复制能力

#### 2.5.4 空态与错误文案（建议）

| 场景 | 提示 |
|---|---|
| 无任何可用渠道 | 暂无可用上游渠道，请联系管理员在「上游渠道」中配置并授权 |
| 渠道存在但无兼容协议 | 该渠道暂无兼容协议，请联系管理员检查渠道 Key 的协议声明 |
| 提交时协议不在兼容集 | 所选协议与上游渠道不兼容 |
| 提交时渠道不存在、无权或已停用 | 上游渠道不可用，请重新选择 |
| 渠道配置在列表加载后发生变化 | 上游渠道配置已变化，请刷新后重新选择 |

### 2.6 权限：哪些渠道对员工可见

创建 Key 时，渠道列表 **不是** 管理端全量渠道，而是员工 **有权使用** 的渠道：

| 渠道 `share_mode` | 是否出现在员工可选列表 |
|---|---|
| `public_pool` | 是（产品线 `status=active`，且渠道内至少存在可用于协议聚合的凭证配置） |
| `grant_only` | 仅当该员工对 **该渠道下至少一把 credential** 有有效授权时出现 |
| `disabled` | 否 |

补充规则：

1. 供应商或产品线非 `active`：不展示
2. 参与协议聚合的凭证必须同时满足：
   - 当前员工可访问：`public_pool` 下为渠道内凭证；`grant_only` 下仅为存在 `credential_employee_grants` 关系行的凭证
   - `status IN ('active', 'cooling')`
   - `weight > 0`
3. `disabled`、`auto_disabled` 或 `weight <= 0` 的凭证不参与协议聚合；`cooling` 为临时状态，保留其协议能力
4. 渠道下没有任何参与聚合的凭证：不展示，避免创建后必然长期不可用
5. `compatibleProtocols` 为上述凭证的 `supported_protocols` 去重并集，并按固定协议顺序返回；遗留空协议声明按现网兼容规则视为 `openai_chat`
6. `credentialCount` 仅统计当前员工可见且参与协议聚合的凭证数，不得返回渠道内其他未授权凭证数量
7. 本版本中的「有效授权」仅指授权关系行存在；授权表当前没有有效期或状态字段
8. **渠道绑定不授予权限**：绑定只缩小调度范围，运行时仍必须重新检查当前授权、共享模式和各层状态
9. 渠道列表按 `providerName`、`productLineName`、`productLineId` 稳定排序，避免弹窗顺序随数据库返回顺序漂移
10. 只读接口计算凭证有效状态时，`cooling` 且 `cool_until IS NULL` 或已到期应视为 effective active，但不在列表请求中回写数据库；尚未到期才视为 effective cooling

### 2.7 数据模型修改

#### 2.7.1 表 `employee_api_keys`

新增字段：

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `product_line_id` | `bigint` | 数据库可空；FK → `product_lines.id`，`ON DELETE RESTRICT` | 绑定的上游渠道（产品线） |
| `binding_mode` | `api_key_binding_mode` | 非空，默认 `product_line` | 区分新绑定 Key 与历史未绑定 Key |

新增枚举：

```text
api_key_binding_mode = legacy_unbound | product_line
```

新增检查约束：

```sql
(
  binding_mode = 'legacy_unbound'
  AND product_line_id IS NULL
)
OR
(
  binding_mode = 'product_line'
  AND product_line_id IS NOT NULL
)
```

安全要求：

- 新建接口只能写入 `binding_mode = 'product_line'`，并强制提供 `product_line_id`
- `legacy_unbound` 只能由本次迁移为存量 Key 标记，任何业务接口均不得创建或修改为该模式
- FK 禁止 `ON DELETE SET NULL`；否则渠道删除会把硬绑定 Key 降级成可全池调度的遗留 Key
- 本版本只允许停用产品线，不支持物理删除；`RESTRICT` FK 对 revoked Key 同样生效，不能用吊销绕过引用约束

索引：

- `employee_api_keys_product_line_idx` on (`product_line_id`)
- `employee_api_keys_employee_product_line_idx` on (`employee_id`, `product_line_id`)

#### 2.7.2 历史数据迁移

| 策略 | 说明 |
|---|---|
| 存量标记 | 存量 Key 设置 `binding_mode='legacy_unbound'`、`product_line_id=NULL` |
| 非员工账号 Key | owner 当前不是 `employee` 的 Key 在迁移中统一置为 `revoked`，不得因未来角色切回 employee 而恢复全池调用 |
| 遗留 Key 调度 | 保持修改前行为：仅按 `protocol` + model route + 公共池/授权调度，**不**强制渠道 |
| 新建 Key | 必须写入 `binding_mode='product_line'` 并携带 `product_line_id`，后端拒绝缺失 |
| 列表展示 | 遗留 Key 渠道列显示「未绑定渠道（遗留）」或「—」 |

> 若业务要求存量 Key 也必须重绑渠道：可另做管理员迁移工具或强制员工重建 Key；**本版本不强制作废存量 Key**。

迁移执行顺序：

1. 新增 nullable、无默认值的 `product_line_id`
2. 创建枚举并以 nullable、无默认值方式新增 `binding_mode`
3. 将全部存量行回填为 `legacy_unbound`
4. 将 owner 角色不是 `employee` 的存量 Key 统一置为 `revoked`，记录数量并形成迁移审计记录
5. 将 `binding_mode` 改为非空，并把新行默认值设置为 `product_line`
6. 增加检查约束、FK 与索引
7. 验证旧写入路径在缺失 `product_line_id` 时会失败，而不是生成新的遗留 Key

以上 DDL/DML 必须在同一 migration 事务内按顺序执行。Drizzle 根据最终 schema 生成的 SQL 需要人工检查和调整，不能直接让存量行先获得 `binding_mode='product_line'` 默认值后再添加 CHECK。

#### 2.7.3 不改动的表

- `upstream_credentials`：继续用 `supported_protocols` 声明单 Key 协议能力
- `product_lines` / `providers`：结构不改；员工接口读取元数据，relay 按请求实时复核状态；渠道继续采用状态停用
- `model_routes`：结构不改；绑定渠道内继续采用显式路由优先、无显式路由时自动发现回退（见 2.9）

### 2.8 接口修改

#### 2.8.1 新增：员工可选上游渠道列表

```http
GET /api/me/upstream-channels
```

**鉴权：** 员工 Session + 已改密 + `role=employee`

**响应示例：**

```json
{
  "success": true,
  "data": [
    {
      "productLineId": 8,
      "productLineCode": "glm-api",
      "productLineName": "智谱 API",
      "productType": "api",
      "shareMode": "public_pool",
      "providerId": 3,
      "providerCode": "zhipu",
      "providerName": "智谱 GLM",
      "compatibleProtocols": ["openai_chat"],
      "credentialCount": 2
    }
  ]
}
```

**过滤逻辑：** 见 2.6。仅返回 `compatibleProtocols.length > 0` 的渠道。

**安全要求：**

- 接口只查询和返回渠道元数据，不读取、不解密、不返回 `secret_encrypted` 或完整上游 Key
- 不返回上游 `baseUrl`；员工始终调用 TokenHub 地址
- 列表接口不得为了复用调度逻辑而产生凭证状态写操作
- 不存在、无权或停用的渠道不应通过响应差异被枚举

#### 2.8.2 修改：创建员工 API Key

```http
POST /api/me/api-keys
```

**请求体（修改后）：**

```json
{
  "name": "本机 Cursor",
  "productLineId": 8,
  "protocol": "openai_chat"
}
```

| 字段 | 修改前 | 修改后 |
|---|---|---|
| `name` | 必填 | 必填（不变） |
| `protocol` | 必填（全局三选一） | 必填，且必须属于该渠道 `compatibleProtocols` |
| `productLineId` | 无 | **新增必填** |

请求字段不得设置默认值：缺失 `name`、`protocol` 或 `productLineId` 均返回参数错误；`name` 服务端 trim 后长度为 1–100，`productLineId` 必须为正整数。

**校验顺序（后端）：**

1. 当前账号为 `employee` 且已改密
2. 参数类型与枚举合法
3. 渠道存在且对当前员工可见（同 2.6）
4. `protocol ∈ compatibleProtocols(productLineId, employeeId)`
5. 写入 `employee_api_keys`：`binding_mode='product_line'`、`product_line_id`、`protocol`、加密 Key 等
6. 操作审计 `api_key.create` 的 `detail` 增加 `bindingMode`、`productLineId`、`protocol`

**创建错误契约：**

| 场景 | HTTP | `code` | 说明 |
|---|---:|---|---|
| 参数缺失或类型错误 | 400 | `invalid_request` | 不应用默认渠道或协议 |
| 渠道不存在、无权或已停用 | 404 | `upstream_channel_unavailable` | 统一响应，避免渠道枚举 |
| 协议不在最新兼容集 | 400 | `channel_protocol_incompatible` | 前后端配置发生变化时要求重新选择 |

**成功响应：** 在现有字段基础上增加渠道摘要，例如：

```json
{
  "success": true,
  "data": {
    "id": 12,
    "name": "本机 Cursor",
    "keyPrefix": "th_xxxx",
    "protocol": "openai_chat",
    "bindingMode": "product_line",
    "productLineId": 8,
    "productLineName": "智谱 API",
    "providerCode": "zhipu",
    "providerName": "智谱 GLM",
    "status": "active",
    "createdAt": "...",
    "key": "th_..."
  }
}
```

#### 2.8.3 修改：列表 / 揭示 / 删除

| 接口 | 变更 |
|---|---|
| `GET /api/me/api-keys` | 每行增加 `bindingMode`、`isLegacy`、`productLineId`、`productLineName`、`providerCode`、`providerName`；遗留 Key 渠道字段为 `null` |
| `POST /api/me/api-keys/:id/reveal` | 按总 PRD 禁止员工再次读取托管副本；服务端不再注册该路由，统一返回 404 |
| `DELETE /api/me/api-keys/:id` | 删除规则不变；删除审计必须保留名称、协议、`bindingMode`、`productLineId` 与渠道摘要 |

列表关联 `product_lines`、`providers` 时必须使用 `LEFT JOIN`，保证 `legacy_unbound` Key 不会从员工或管理员列表中消失。

#### 2.8.4 管理端（联动，小改）

现有管理员员工 Key 列表与复制接口必须同步修改：

- 列表/详情应展示绑定渠道，避免只显示协议造成误解
- 管理员 reveal 响应与操作审计详情带上 `bindingMode`、`productLineId`
- 遗留 Key 明确标记「未绑定渠道（遗留）」
- 管理员 reveal 继续使用 `Cache-Control: no-store`、`Pragma: no-cache`，且每次读取必须写操作审计

### 2.9 请求调度修改（硬绑定）

#### 2.9.1 规则

当请求携带的员工 Key **已绑定** `product_line_id` 时：

1. 仍根据 Key 的 `protocol` 校验入口路径是否匹配（与现网一致）
2. 从鉴权查询结果读取 `binding_mode`、`product_line_id`，不得信任客户端 header/body 中的渠道字段
3. 在解析模型、生成候选、错误分类和重试之前，先把凭证与路由范围收窄到 `product_line_id = Key.product_line_id`
4. 每次请求实时复核：供应商/产品线状态、`share_mode`、员工 credential grant、凭证状态/权重、凭证协议能力
5. 选凭证时，仅在绑定产品线内按 priority/weight/健康度调度
6. 失败重试（401 摘除、429 冷却、5xx 换 Key 等）只在绑定产品线内换凭证，禁止跨渠道
7. 若授权撤销、共享模式变化、渠道停用、凭证移除或协议能力变化，请求立即按最新配置失败，不得回退到其他渠道

当 Key 为遗留数据（`binding_mode='legacy_unbound' AND product_line_id IS NULL`）：

- 保持修改前的全池调度行为
- 仅该模式允许无渠道调度；任何不满足检查约束的 Key 均视为无效 Key，禁止进入 relay

#### 2.9.2 显式模型路由与自动发现路由

绑定 Key 保留现有两类模型路由能力，但判定范围必须先限定到绑定产品线：

1. 若绑定产品线内存在该 `client_model` 的 enabled `model_routes`，使用这些显式路由
2. 若绑定产品线内不存在该模型的显式路由，则仅在该产品线内按 `allow_auto_route=true` + credential `discoveredModels` 自动路由
3. 其他产品线存在同名显式路由，不得阻断绑定产品线的自动发现回退
4. 若绑定产品线内存在 enabled 显式路由，但路由权重为 0 或无匹配协议凭证，按该渠道不可用处理，不自动回退且不跨渠道；disabled 路由不计入显式路由存在性判断
5. 遗留 Key 完全保持修改前的全局显式路由/自动路由判定逻辑

#### 2.9.3 `GET /v1/models`

- 绑定 Key：只返回绑定产品线内，当前员工按最新权限和状态实际可调用的显式路由模型与自动发现模型
- 遗留 Key：保持修改前的全池模型列表
- 模型列表和实际请求必须调用同一套渠道、授权、协议、状态过滤逻辑，避免「列表可见但调用越界」
- `/v1/models` 只读，不修改凭证状态；查询时按 effective status 把已过期 cooling 视为 active，持久状态恢复由调度/健康维护逻辑负责

#### 2.9.4 错误语义

所有错误继续使用请求协议对应的 OpenAI/Anthropic 原生响应 envelope：

| 场景 | HTTP | `code` | 错误语义 |
|---|---:|---|---|
| 绑定渠道内没有该 model 的显式或自动路由 | 404 | `model_not_found` | 当前 Key 绑定的上游渠道不支持该模型 |
| 绑定渠道内匹配凭证全部处于尚未到期的 effective cooling | 429 | `model_channels_cooling` | 返回 `Retry-After` |
| 模型已配置但渠道内无可用凭证 | 503 | `model_unavailable` | 绑定渠道暂无可用上游凭证 |
| 当前授权已撤销或渠道已停用 | 503 | `bound_channel_unavailable` | Key 仍保持绑定，不跨渠道 |
| 协议与入口不匹配 | 与现网一致 | 与现网一致 | Key 协议与请求路径不一致 |

错误分类顺序固定为：绑定目标/授权不可用 → 模型不存在 → 全部 cooling → 其他凭证不可用，避免其他渠道的配置影响绑定渠道错误语义。

#### 2.9.5 审计

- 鉴权 principal 增加 `bindingMode`、`productLineId`
- 成功或已选择候选的请求，`request_audits.product_line_id` 记录实际命中的产品线
- 绑定 Key 在选出候选前失败时，`request_audits.product_line_id` 记录 principal 的绑定产品线，便于排查
- 遗留 Key 在选出候选前失败时，该字段保持 `NULL`
- 员工 Key 绑定渠道后，不能通过换 model、重试或 Responses affinity 绕到其他渠道

### 2.11 验收标准

1. **创建顺序：** 未选渠道时无法选择有效协议或提交；必须先渠道后协议。
2. **协议过滤：** 协议下拉仅出现该渠道兼容协议；切换渠道后选项与选中值正确重置。
3. **权限：** `public_pool` 渠道对员工可见；`grant_only` 仅聚合该员工已授权凭证；`disabled`、空凭证、无有效聚合凭证渠道不可见。
4. **落库：** 新建 Key 为 `binding_mode='product_line'` 且 `product_line_id`、`protocol` 正确；业务接口不能创建 `legacy_unbound`；审计可追溯。
5. **调度：** 绑定 Key 只命中绑定渠道凭证；失败不落到其他供应商/产品线。
6. **列表：** 员工可见渠道名 + 协议；遗留 Key 不报错，渠道列有明确展示；员工列表不提供 reveal/复制操作。
7. **兼容：** 遗留未绑定 Key 仍可按旧逻辑调用（回归）。
8. **安全：** 员工接口不得返回上游 secret / 完整官方 Key；员工 Key 明文仅创建时展示一次，之后仅管理员可审计读取。
9. **模型发现：** 绑定 Key 的 `/v1/models` 仅返回绑定产品线实际可调用模型；遗留 Key 保持全池列表。
10. **自动路由：** 绑定渠道内没有显式路由时可按现有自动发现回退；其他渠道的显式路由不干扰该判断。
11. **运行时变更：** 撤销 grant、切换 share mode、停用供应商/产品线、停用凭证或移除协议后立即生效，且任何失败均不跨渠道。
12. **删除安全：** 有绑定 Key 时产品线不能被 FK 自动置空；禁止出现「硬绑定 Key 因删除渠道变成遗留全池 Key」。
13. **角色隔离：** admin/auditor 不能通过员工 API 创建调用 Key；employee 转为 admin/auditor 时已有 Key 全部 revoke，改回 employee 不自动恢复；员工不能访问管理接口。

### 2.12 非目标与明确不做

1. 创建时选择「某一把」上游 API Key（只选渠道）
2. 员工端修改已创建 Key 的渠道/协议（如需变更：删除后重建）
3. 自动把历史 Key 批量绑定到某默认渠道
4. 上游余额、按 Key 额度统计
5. 改变「员工之间日志隔离」规则
6. 为管理员或审计员开放员工调用 Key（角色隔离沿用总 PRD）
7. 员工在创建完成后再次读取托管的 API Key 明文（仅管理员可审计 reveal）

### 2.13 实现备注（给开发）

1. **渠道协议聚合** 在服务端实现为独立、只读的元数据函数，供 GET 列表和 POST 校验共同调用；前端不重复计算。
2. 元数据函数只查询必要字段，不加载 `secret_encrypted`，不回写 cooling 状态，不产生数据库写操作。
3. 元数据与模型列表通过纯函数计算 effective credential status，确保 cooling 到期后即使不写库，模型发现与实际调度也得到一致结论。
4. 调度函数可以加载加密凭证并维护 cooling 状态，但不得把包含 secret 的对象直接传给员工接口。
5. 渠道兼容协议来自凭证级 `supported_protocols` 的规范化并集；若后续增加产品线级协议字段，再统一收敛，不阻塞本版本。
6. 所有 relay 调用点通过 principal 传递绑定信息；函数参数不得只传 `employeeId + protocol` 后在下游重新猜测渠道。
7. 候选必须在排序和重试之前完成渠道过滤，不能生成全池候选后再在部分调用点事后过滤。
8. 硬绑定会削弱跨渠道容灾，这是本版本明确产品选择；错误提示与员工接入文档需说明。

### 2.14 最低测试矩阵

1. **Migration**
   - 从 0002 数据库带存量 Key 升级；存量行正确标记为 `legacy_unbound`
   - 非 employee owner 的存量 Key 被 revoke，角色改回 employee 后仍不可用
   - 新 Key 必须有产品线；旧写入逻辑缺少产品线时被检查约束拒绝
   - 删除有绑定 Key 的产品线被 FK 拒绝，不会把 `product_line_id` 置空
2. **渠道列表与创建**
   - public、grant_only、disabled；供应商/产品线停用；空凭证渠道
   - active、cooling、disabled、auto_disabled、weight=0 的协议聚合口径
   - grant_only 同渠道中，未授权凭证的协议和数量不泄露
   - 缺字段、越权渠道、协议错配、列表后配置变化
   - 创建结果展示明文一次；员工 reveal 路由返回 404；管理员 reveal 仍可用并写审计
3. **硬绑定重试**
   - 两个产品线配置同一个 client model；绑定 A 的请求绝不命中 B
   - A 内首凭证分别触发 401、429、5xx、网络错误，允许换 A 内第二凭证，B 调用数始终为 0
4. **三协议与模型发现**
   - Chat、Responses、Responses compact、Messages、Messages count_tokens 均不跨产品线
   - `/v1/models` 仅列绑定产品线模型
   - 绑定产品线显式路由、disabled 路由被忽略后的自动发现回退、其他产品线同名显式路由不干扰
   - Responses affinity 不得把请求带到其他产品线
5. **运行时配置变化**
   - 撤销 grant、public 切 grant_only、供应商/产品线停用、凭证停用、移除协议、禁用路由均立即生效
   - 上述失败都不跨渠道
   - employee 改为 admin/auditor 时 active Key 全部 revoke；改回 employee 后不自动恢复
6. **遗留兼容与列表**
   - `legacy_unbound` Key 保持旧全池调度
   - 员工/管理员列表通过 LEFT JOIN 保留遗留 Key，渠道摘要为 `NULL`
7. **发布门禁**
   - server unit test、数据库 mock 集成测试、native protocol mock 集成测试、server/web build 全部通过

### 2.15 发布与回滚策略

#### 发布顺序

1. 先关闭员工 Key 创建入口或进入维护窗口，避免 migration 与旧写入并发
2. 备份数据库并执行 migration；此时旧写入路径因检查约束而 fail-closed
3. 停止或摘流所有旧 relay 实例，部署支持 `binding_mode/product_line_id` 的新后端
4. 验证 Chat、Responses、Messages 与 `/v1/models` 均已读取绑定信息
5. 再发布员工前端并重新开放 Key 创建入口
6. 发布期间禁止新旧 relay 实例混跑；否则同一绑定 Key 可能在旧实例上恢复全池调度

#### 回滚约束

- 尚未开放新建绑定 Key：可回滚前端，后端和 migration 可按常规方案处理
- 已创建绑定 Key：不得回滚到不识别绑定字段的旧 relay；可先关闭创建入口并回滚前端，但后端必须保持 binding-aware
- 如需数据库级回滚，必须先吊销或迁移所有 `binding_mode='product_line'` Key，并经过人工确认
- 优先 roll forward 修复，禁止通过清空 `product_line_id` 规避回滚问题

## 3. 删除功能

无正式产品功能删除。

本版本不删除总 PRD 已授权的菜单、接口或角色能力；仅收紧 **新建** 员工 API Key 的创建条件与调度约束。
存量未绑定渠道的 Key **不删除**，按遗留策略继续可用。

当前实现中若 admin/auditor 可进入 `/me`，属于与总 PRD 角色隔离规则不一致的实现偏差；恢复为仅 employee 可访问不视为删除正式产品能力。

当前实现中的员工自助 reveal 同样与总 PRD「托管副本仅管理员可读取」不一致；移除员工 reveal 入口属于安全基线修正。员工仍可在创建成功时查看并复制明文一次，管理员 reveal 能力不变。
