# TokenHub v0.0.1 工程规格

| 项 | 内容 |
|---|---|
| 版本 | `v0.0.1` |
| 产品基线 | 首次正式发布架构 |
| 状态 | 开发与全新数据库隔离验证完成，生产环境待部署 |
| 员工页面 | `/me/keys` |
| 模型接口 | `/v1/models`、Chat、Responses、Responses compact、Messages、Messages count_tokens |

本文定义 v0.0.1 的数据模型、接口、调度、安全和验收规则。所有员工 API Key 必须绑定一个上游渠道和一种协议，系统不存在未绑定渠道的员工 Key，也不存在跨渠道候选池。

---

## 1. 版本目标

1. 员工按“上游渠道 → 兼容协议 → 名称”创建内部 API Key。
2. 每把 Key 的模型列表、模型解析、凭证选择、重试和 Responses 亲和均固定在绑定渠道内。
3. 渠道绑定不授予权限；共享模式、授权、状态、权重和协议在每次请求时重新校验。
4. 员工只在创建成功时查看一次完整 Key，管理员读取托管副本必须经过权限校验与操作审计。
5. employee、admin、auditor 的页面和接口严格隔离。
6. 数据库从结构上拒绝无渠道 Key，Relay 从鉴权开始拒绝无效渠道关联。

### 1.1 非目标

- 不绑定到某一把具体上游凭证，只绑定 ProductLine。
- 不允许创建后修改渠道或协议；需要变更时删除并重建 Key。
- 不做 Chat、Responses、Messages 之间的协议转换。
- 不提供跨渠道容灾。
- 不提供员工端 Key 明文找回。
- 不提供上游余额或商业计费能力。

---

## 2. 角色边界

| 角色 | 页面 | Key 权限 |
|---|---|---|
| employee | `/me/*` | 创建、查看摘要、删除自己的 Key；明文仅创建时出现 |
| admin | `/admin/*` | 管理员工；在操作审计约束下读取员工 Key 托管副本 |
| auditor | `/admin/*` 只读子集 | 不能创建、删除或读取员工 Key 明文 |

规则：

1. `/api/me/*` 只允许已完成改密的 active employee。
2. `/api/admin/*` 按 admin/auditor 的路由权限授权。
3. `/v1/*` 只接受 active employee 名下未过期、未吊销的 Key。
4. employee 变为 admin 或 auditor 时，角色更新与其全部 active Key 吊销在同一事务中完成。
5. 用户再次变为 employee 时，已吊销 Key 不自动恢复。
6. 页面不提供管理端与员工端之间的切换入口。

## 3. 上游渠道元数据

### 3.1 接口

```http
GET /api/me/upstream-channels
```

响应项：

```json
{
  "productLineId": 12,
  "productLineCode": "glm-coding",
  "productLineName": "GLM Coding Plan",
  "productType": "coding_plan",
  "shareMode": "grant_only",
  "providerId": 3,
  "providerCode": "glm",
  "providerName": "智谱",
  "compatibleProtocols": ["openai_chat", "anthropic_messages"],
  "credentialCount": 2
}
```

接口不得查询或返回：

- `secret_encrypted` 或完整上游 Key；
- 上游 Base URL；
- 员工无权使用的凭证数量、协议和健康详情。

### 3.2 渠道可见性

渠道必须满足 Provider 与 ProductLine 均为 active，并至少存在一条当前员工可使用的有效凭证：

| `share_mode` | 规则 |
|---|---|
| `public_pool` | 渠道内符合条件的凭证对 active employee 可用 |
| `grant_only` | 只聚合存在 `credential_employee_grants` 关系的凭证 |
| `disabled` | 不返回 |

参与聚合的凭证必须：

- `status` 的有效状态为 `active` 或尚未结束的 `cooling`；
- `weight > 0`；
- 至少声明一个支持协议。

`disabled`、`auto_disabled`、非正权重和空协议集合不参与聚合。`compatibleProtocols` 是可见凭证协议的去重并集，固定顺序为：

```text
openai_chat → openai_responses → anthropic_messages
```

`credentialCount` 只统计当前员工可见且参与聚合的凭证。渠道按 Provider 名称、ProductLine 名称和 ProductLine ID 稳定排序。

只读接口使用查询时刻计算 effective credential status；冷却时间为空或已到期时视为 active，但查询本身不写数据库。

## 4. 员工 Key 创建

### 4.1 页面流程

`/me/keys` 的字段顺序固定为：

1. 上游渠道；
2. 兼容协议；
3. 名称。

交互规则：

1. 弹窗打开时重新拉取渠道列表。
2. 未选择渠道时协议不可选、创建不可提交。
3. 选择渠道后默认选中该渠道第一个兼容协议。
4. 切换渠道时必须清除原协议并按新渠道重新选择。
5. 渠道为空、加载失败、协议为空和提交失败均提供明确状态与重试入口。
6. 创建成功后直接展示完整 Key 和复制按钮。
7. 员工确认已安全保存后才能关闭结果页。
8. 列表只展示 Key 前缀、渠道、协议、状态和时间，不提供明文读取。
9. 删除使用确认框与 Key 名称输入两步确认。

### 4.2 创建接口

```http
POST /api/me/api-keys
Content-Type: application/json

{
  "name": "本机 Cursor",
  "productLineId": 12,
  "protocol": "openai_responses"
}
```

所有字段必填：

| 字段 | 规则 |
|---|---|
| `name` | 去除首尾空白后 1–100 字 |
| `productLineId` | 正整数，且必须属于当前员工最新可选渠道集合 |
| `protocol` | 系统协议枚举，且必须属于该渠道最新兼容协议集合 |

服务端在创建事务内：

1. 锁定 owner 员工行，确认仍为 active employee 且已完成改密；
2. 查询并锁定 Provider、ProductLine、参与校验的凭证与授权行；
3. 重新计算渠道可见性和兼容协议；
4. 生成 Key、哈希和用途隔离的加密副本；
5. 写入非空 ProductLine、协议和 Key 数据；
6. 写入包含渠道和协议摘要的操作审计。

创建响应设置 `Cache-Control: no-store` 与 `Pragma: no-cache`，完整 Key 只在本次响应返回。

### 4.3 创建错误

| 场景 | HTTP | 错误码 |
|---|---:|---|
| 字段缺失、类型错误、名称或枚举不合法 | 400 | `invalid_request` |
| 渠道不存在、无权、已停用或没有可用凭证 | 404 | `upstream_channel_unavailable` |
| 协议不在渠道最新兼容集合 | 400 | `channel_protocol_incompatible` |
| owner 已不满足 employee 调用条件 | 403 | `forbidden` |

## 5. 数据模型

### 5.1 `employee_api_keys`

关键字段：

| 字段 | 约束 | 说明 |
|---|---|---|
| `employee_id` | NOT NULL，FK → `employees.id` | Key 所有者 |
| `product_line_id` | NOT NULL，FK → `product_lines.id`，ON DELETE RESTRICT | 唯一绑定渠道 |
| `protocol` | NOT NULL，`relay_protocol` | 唯一绑定协议 |
| `key_hash` | NOT NULL，唯一 | 鉴权索引 |
| `key_encrypted` | NOT NULL | 管理员受审计读取的用途隔离托管副本 |
| `status` | NOT NULL | `active` 或 `revoked` |
| `expires_at` | 可空 | 到期时间 |

索引：

- `employee_api_keys_product_line_idx(product_line_id)`；
- `employee_api_keys_employee_product_line_idx(employee_id, product_line_id)`。

`product_line_id` 是员工 Key 唯一的渠道关联。名称、协议、ProductLine 和加密托管副本均要求显式写入；非空约束和 RESTRICT 外键共同保证：

- 任何写入路径都不能创建无渠道 Key；
- 被 Key 引用的 ProductLine 不能删除；
- Key 不会因为渠道删除而失去绑定关系。

### 5.2 数据库基线

v0.0.1 使用全新数据库执行唯一初始 Migration 和最小种子。开发环境数据库需要重新创建后执行：

```sh
pnpm db:migrate
pnpm db:seed
```

## 6. Key 查询、删除与管理员读取

### 6.1 员工列表

```http
GET /api/me/api-keys
```

每行必须包含：

- `id`、`name`、`keyPrefix`、`status`；
- `protocol`；
- `productLineId`、`productLineName`；
- `providerCode`、`providerName`；
- `createdAt`、`lastUsedAt`。

关联 ProductLine 和 Provider 使用内连接；数据库不允许无渠道行。

### 6.2 员工删除

```http
DELETE /api/me/api-keys/:id
```

员工只能删除自己的 Key。删除审计记录名称、协议、ProductLine 与渠道摘要。员工端不注册 reveal 路由。

### 6.3 管理员读取

管理员员工详情中的 Key 列表展示绑定渠道和协议。管理员读取托管明文时必须：

1. 通过 admin 权限校验；
2. 校验加密副本与 Key 哈希一致；
3. 返回 `Cache-Control: no-store` 与 `Pragma: no-cache`；
4. 写入 `employee_api_key.reveal` 操作审计；
5. 在响应与审计中携带 ProductLine、Provider 和协议摘要。

auditor 无权执行该操作。

## 7. Relay 渠道硬边界

### 7.1 鉴权 principal

Relay 鉴权从数据库读取：

- employee 与 Key ID；
- Key 协议；
- 非空正整数 `productLineId`；
- employee 名称、手机号和部门。

客户端不能通过 Header、Body 或模型名指定渠道。ProductLine 缺失或非法时鉴权失败，不能进入路由阶段。

### 7.2 运行时访问校验

每次模型查询和调用均重新校验：

- employee、Provider、ProductLine 状态；
- ProductLine `share_mode`；
- `grant_only` 的凭证授权；
- 凭证状态、冷却时间、权重和协议；
- 模型显式路由或自动发现结果。

候选在显式路由判定、自动发现、排序和加权前按 `productLineId` 过滤。任何错误、重试或亲和场景都不能扩大该集合。

### 7.3 模型解析

1. 在绑定 ProductLine 内查询目标 `client_model` 的 enabled 显式路由。
2. 存在 enabled 显式路由时只使用显式路由；权重为 0 或凭证不可用时不回退自动发现。
3. disabled 显式路由不参与判定。
4. 没有 enabled 显式路由时，仅当 ProductLine 开启 `allow_auto_route` 且凭证发现模型包含目标模型时允许自动路由。
5. 其他 ProductLine 的同名路由或发现结果不能影响当前请求。

### 7.4 凭证选择与重试

1. 候选按路由 priority、凭证 priority 分层。
2. 同层按 `routeWeight × credentialWeight` 加权。
3. 单次请求不重复尝试同一凭证，默认最多尝试 3 条候选。
4. 401/403 自动停用当前凭证；429 将当前凭证置为冷却；5xx 和首字节前网络错误切换绑定渠道内下一凭证；400 不重试。
5. 流式响应首字节发出后不再切换凭证。
6. 客户端断开时取消上游请求并完成审计。

### 7.5 Responses 亲和

`previous_response_id` 对应的亲和记录包含 credential、ProductLine 与 upstream model。继续请求必须同时匹配三者，并且 ProductLine 必须等于 Key 的绑定渠道：

- 无亲和记录：`409 response_affinity_not_found`；
- 记录跨渠道或目标候选不可用：`503 response_affinity_unavailable`；
- 不允许重新分配到其他凭证或渠道。

### 7.6 模型列表

`GET /v1/models` 只返回绑定 ProductLine 和 Key 协议下当前真实可调用的模型。模型列表与实际调用共用状态、授权、协议、显式路由和自动发现口径，并保持只读。

## 8. 错误契约

| 场景 | HTTP | 错误码 |
|---|---:|---|
| Key 无效、过期、吊销或 owner 不可调用 | 401 | `invalid_api_key` |
| Provider、ProductLine 或渠道授权不可用 | 503 | `bound_channel_unavailable` |
| 绑定渠道内不存在目标模型 | 404 | `model_not_found` |
| 所有匹配凭证均处于有效冷却期 | 429 | `model_channels_cooling` |
| 模型已配置但无可用匹配凭证 | 503 | `model_unavailable` |
| Responses 亲和记录不存在 | 409 | `response_affinity_not_found` |
| Responses 亲和目标不可用 | 503 | `response_affinity_unavailable` |

429 响应包含 `Retry-After`。OpenAI 协议使用 OpenAI envelope，Anthropic Messages 使用 Anthropic envelope；Anthropic `error` 对象保留确定性 `code` 字段。所有响应包含 TokenHub request ID，不暴露上游 Secret、Base URL 或未授权渠道信息。

## 9. 审计与安全

1. API Key 哈希用于鉴权，加密副本使用独立加密用途。
2. 员工渠道接口从查询层排除 Secret 与 Base URL。
3. 创建、删除、管理员读取和角色变更写入操作审计。
4. Relay 成功、参数错误、配额拒绝、上游失败和取消均写调用审计。
5. 候选产生前的失败使用 principal 中的 ProductLine 记录渠道归属。
6. 选出候选后记录 Provider、ProductLine、Credential、上游模型、重试轨迹和终态。
7. 请求头使用白名单保存，Authorization 与 `x-api-key` 不进入审计正文。
8. 管理员 Key 明文读取响应禁止缓存。

## 10. 验收矩阵

### 10.1 数据库与 API

- 全新 PostgreSQL 16 数据库完整执行唯一初始 Migration。
- `product_line_id` 为 NOT NULL；无渠道直接写入失败。
- 删除被 Key 引用的 ProductLine 被 RESTRICT FK 拒绝。
- public_pool、grant_only、停用渠道、各凭证状态与权重的可见性正确。
- grant_only 不泄露未授权凭证协议和数量。
- 创建接口拒绝缺字段、越权渠道和协议错配。
- 创建时配置发生变化会在事务内重新校验，不产生失效 Key。
- employee/admin/auditor 边界、角色变更吊销和反向不恢复通过。
- 员工明文仅创建响应出现；员工 reveal 为 404；管理员 reveal 禁止缓存并写审计。

### 10.2 渠道隔离

- 渠道 A、B 配置相同客户端模型，绑定 A 的 Key 对 B 的调用数始终为 0。
- Chat、Responses、Responses compact、Messages、Messages count_tokens 全部只使用 A。
- 401、429、500 和网络错误只在 A 内切换凭证。
- `/v1/models` 不返回 B 独有模型。
- B 的 Responses 亲和记录不能使 A Key 越界。
- A 停用后所有协议返回确定性错误，失败审计仍归属 A。
- 显式路由、自动发现、零权重、冷却和不可用错误分类通过单元矩阵。

### 10.3 工程门禁

- 服务端默认单元测试通过。
- Relay Mock、Native Protocol Mock、v0.0.1 API/数据库集成和硬绑定集成通过。
- Server 与 Web 生产构建通过。
- Drizzle schema/migration 检查和 `git diff --check` 通过。
