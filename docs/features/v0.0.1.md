### 1. 需求概述

#### Problem Statement

作为用 Cursor / Claude Code 的开发者，我只想改一个 Base URL 就继续用原来的官方 SDK。试点网关却要求「一把 Key 绑死一条渠、一种协议」，换模型或换客户端就要重建钥匙；网关若再做协议翻译，thinking / 工具调用还可能被改坏。

作为平台方，我需要从第一天就按「虚拟钥匙 → 池 → 渠」记账和选路，而不是把调用方钥匙钉在单条上游上。但 0.0.1 还不必真做多路容灾——池里先有一条活路就行。

#### Solution

提供 Token Hub 最小网关：两个原生端点、零转换、SSE 原样流、断开即停上游。调用方持一把 **VK**（`fab-…`），不持有上游官方 Key。VK 挂在一个**池**上，本版该池只有一条**渠**（一个兼容上游）。OpenAI 端点只转发 OpenAI 兼容上游，Anthropic 端点只转发 Anthropic 兼容上游，绝不互转、不跨协议 Fallback。

结束后以厂家返回的 `usage` 为准记 Token；没有 `usage` 才用估算。上游限流头原样回给客户端。

#### Out of Scope

- 上游多 Key 轮转、加密钥匙柜、401 自动停用（0.0.2）
- VK 过期、模型白名单产品化、申请审批（0.0.3 / 0.0.8）
- 同模型多渠 failover、加权、路由审计 UI（0.0.4）
- 团队/分组隔离（0.0.5）
- 限流硬拒绝、熔断半开（0.0.6）
- 月预算软硬闸、流式中实时估 Token 给预算看（0.0.7；本版只在**响应里**贯彻厂家 usage）
- 响应缓存、Prompt Cache 运营（0.0.8）
- Embedding / Batch、ROI 选路、Commerce、SSO、管理后台页面
- 改试点 `/ai/*` 热路径或继续长 `employee_api_keys.product_line_id + protocol` 硬绑定
- `x-fabric-context` / `fabric_context` 业务语义（0.0.3 预留头即可，本版可忽略）

### 3. 技术方案

**D1 零转换**  
请求体、响应体、SSE 事件数据不改写（除本网关必须加的 hop-by-hop 传输头）。thinking、`cache_control`、`tool_choice`、工具调用块必须原样到达对端。

**D2 端点与协议绑定在路径上，不绑在 VK 上**  
`POST /v1/chat/completions` 只转发 OpenAI 兼容上游；`POST /v1/messages` 只转发 Anthropic 兼容上游。VK **不**带「只能用某一协议」字段。本版一把种子 VK 两个端点都能调（为 0.0.3 的「一把两端口」留好形状；0.0.3 再加过期和模型范围）。

**D3 身份形状按 HLD**  
`VirtualKey`（`fab-`）→ `ChannelPool` → `Channel`（挂 `ProviderKey`）。调用方只出示 VK。本版池内恰好一条可用渠。禁止「VK 直接外键到单条上游 Key」或试点那种「钥匙钉死 product line + protocol」。

**D4 本版调度**  
池内一路：能通就打这一路；不通则按该端点协议返回上游错误或 502/503。不做换渠重试、不做模型 Fallback。

**D5 流式**  
`stream=true`（及 Anthropic 等价）时 SSE 透传，不攒完全文。客户端断开则取消上游请求。流式响应不拿来做可复用响应缓存（#57 约束，本版本来也无缓存）。

**D6 计量可见性**  
优先把上游 `usage` 原样放在非流式 JSON 或流式最终 chunk 里回给客户端。无 `usage` 时允许估算，但须能区分来源。本版不提供用量查询 HTTP；自动化只断言**响应里**的 usage 与假上游一致。

**D7 限流头**  
上游响应中的 `x-ratelimit-*`（及 Anthropic 等价限流头）回传给客户端，网关不吞掉。

**D8 鉴权头跟客户端协议**  
OpenAI 端点：`Authorization: Bearer fab-…`  
Anthropic 端点：`x-api-key: fab-…`（也可接受 Bearer，避免部分代理只转一种头）  
无效 / 未知 VK → 401，错误体用**该端点**的原生 envelope，不泄露上游 Secret。

**D9 种子**  
开发与测试用：一把 `fab-` VK、一个池、一条渠、一个上游。上游在自动化里指向假上游；手测可指向真实兼容服务。

**D10 栈（HLD 附录 B，已定）**  
网关语言 **Go**。V1 单进程部署。新网关不 import 试点 Fastify 选路/硬绑定鉴权。现有 Node 工作区仅作对照，不是本 feature 的实现载体。

### 4. 接口契约

客户端 **Base URL = Token Hub Origin**（不要带 `/v1` 后缀，也不要带试点的 `/ai`）。

| 方法 | 路径 | 协议 | 上游 |
|------|------|------|------|
| POST | `/v1/chat/completions` | OpenAI Chat Completions | 池内 OpenAI 兼容渠 |
| POST | `/v1/messages` | Anthropic Messages | 池内 Anthropic 兼容渠 |

- 请求 JSON / SSE 与官方协议一致；网关不要求额外字段。  
- 成功：上游状态与 body（或 SSE 流）透传。  
- 鉴权失败：401 + 该协议错误 envelope。  
- 池内无匹配协议的渠：503，语义为 provider/channel unavailable；**不得**改打另一协议的渠。  
- 上游 4xx/5xx：按 D1 透传状态与 body（本版不换渠）。  

VK 明文只在种子/创建时存在；运行时用哈希校验（具体哈希算法实现期选，不写进调用方契约）。

### 6. 验收标准

#### User Stories

1. 作为 Cursor 用户，我只改 Base URL 为 Token Hub Origin，仍用 OpenAI 写法调 `/v1/chat/completions`，以便不换 SDK。  
2. 作为 Claude Code 用户，我只改 Base URL 为 Token Hub Origin，仍用 Anthropic 写法调 `/v1/messages`，以便不换客户端。  
3. 作为开发者，我发出带 thinking / 工具调用字段的请求，并在响应里原样看到它们，以便网关不破坏官方协议。  
4. 作为开发者，当 OpenAI 兼容上游不可用时，我的 Chat Completions 请求不会被偷偷改成 Claude，以便协议不会错乱。  
5. 作为开发者，我能在客户端看到上游带回的限流剩余头，以便区分「厂家在限」还是「网关挂了」。  
6. 作为开发者，流式对话时字是一块块出现的，以便手感接近直连。  
7. 作为开发者，我在 IDE 点停止后，上游不再继续生成，以便不再空烧 Token。  
8. 作为开发者，非流式或流式结束后，我看到的 usage 与厂家声明一致（无 usage 时才是估算），以便对账有依据。  
9. 作为开发者，用错或伪造的 VK 会得到该协议的 401，以便钥匙无效时行为可预期。  
10. 作为平台方，种子数据是 VK→池→一条渠，以便后面加多渠时不必推翻钥匙模型。

#### Testing Decisions

**缝 T1（已确认）**：只在进程内 HTTP 上测新网关：

- `POST /v1/chat/completions`（含 `stream`）  
- `POST /v1/messages`（含 stream）
