# v0.1.0 — Fabric · Token Hub 公测就绪

## Part A — 版本级叙事

### 版本目标

发布 **KodaX Fabric 核心模块 Token Hub** 的第一个「公司内可大范围公测」版本。

- 产品：KodaX Fabric  
- 本版本范围：仅 **Token Hub 核心模块**（仓库内既有 TokenHub 实现）  
- 基线：v0.0.5（`tokenhub.haizhi.com` 已可访问，已有同事用 Key + Claude Code）  
- 进度口径：Token Hub 进度 = Fabric 当前进度  

### 本版本范围

**做（0.1.0 must）**

将公测硬门槛 **E1～E10** 从「部分满足」收到「可签字验收」：

| ID | 门槛 |
|----|------|
| E1 | 可重复发布 |
| E2 | 数据可托底（备份 + 恢复验证） |
| E3 | 渠道策略成文 |
| E4 | 账号生命周期 |
| E5 | 配额默认合理 |
| E6 | 故障可感知（最低配） |
| E7 | 问题有入口 |
| E8 | 安全底线 |
| E9 | 接入可自助（双协议） |
| E10 | 核心路径不回退（回归清单） |

**裁剪原则（grill 冻结）**

- 落地类型：发布/公测就绪（非结构大拆、非先做大新功能）  
- 完成定义：**M5** — 生产/公测托底为主，只补挡住扩大使用的 P0  
- 清单裁法：**L4** — 公测准入为骨架 + 现网痛点；PRD 只拦 P0 安全/隔离/数据  
- 协议：双协议（Claude Code / Cursor 等）；一种工具建议一把 Key  

**不做（明确排除）**

- Token ROI / 浪费检测 / 文件归因  
- Budget Waterfall、Commerce、完整多租户组织  
- SSO、跨渠道容灾、协议互转  
- 为「更像 Fabric」而做的 monorepo 大目录重构（可用文档声明模块关系）

### 推荐收口顺序

```text
① S1 公测章程 + 配置基线成文     ← 第一刀
② S2 发布 runbook + 备份恢复演练
③ S3 接入自助（E9）打磨
④ S4 故障怎么查（E6）一页纸
全程：只修挡住公测的代码 P0
```

### 版本级验收

- E1～E10 均有可展示的验收证据（文档签字项、演练记录或自动化/清单勾选）  
- 现有 Claude Code（及约定的第二协议客户端）调用路径不回退  
- 版本号与发布说明将 Token Hub 表述为 Fabric 核心模块；不宣称 Fabric 全能力完成

## FEATURE_001: Token Hub 核心模块公测收口

### 1. 需求概述

**问题**

Token Hub（v0.0.5）已在公司内网部署并有真实使用，但 E1～E10 均为「做了一些、不敢称完成」，不足以支撑公司内大范围公测。负责人不清楚下一步，容易误入功能扩张或无限加固。

**目标**

在 **不扩展 Fabric 非核心模块** 的前提下，把 Token Hub 收到 v0.1.0：**公司内部可大范围公测**。

**成功标准**

- 公测章程与配置基线成文并可执行（S1 优先）  
- E1～E10 均可签字验收  
- 不引入 ROI/Commerce/SSO 等 0.1.0 排除项  

### 2. 影响范围

| 类型 | 路径/区域 | 说明 |
|------|-----------|------|
| 文档（主） | `docs/`（公测章程、发布/备份 runbook、接入指南、故障排查、回归清单） | S1～S4 主体 |
| 部署 | `deploy/`（README、backup、compose 流程与演练记录） | E1/E2 |
| 配置/种子 | 默认配额、系统设置、渠道策略说明 | E3/E5；能成文锁定的优先成文 |
| 代码（按需） | `server/`、`web/` | **仅** 挡住公测的 P0；无则大功能开发 |
| 版本与清单 | `package.json`、本文件、`FEATURE_LIST.md`、CHANGELOG（发布时） | v0.1.0 发布 |

_具体文件列表待 `/to-spec` / `/to-tickets` 细化。_

### 3. 技术方案

- **策略**：文档与运维闭环优先；代码只补 P0 洞（M5）。  
- **运行基线**：维持现有 Node/Fastify + Vue + PostgreSQL + Redis + `deploy/` 部署，不做 HLD 级 Go/ClickHouse 迁移。  
- **模块叙事**：对外/对内文档统一「Fabric · Token Hub 核心模块」；工程包名 `tokenhub` 可暂留，避免 0.1.0 无谓大改。  
- **验收方式**：每条 E 对应证据（文档章节、演练日期、检查单），而非仅「感觉做过」。  

_细节待 `/to-spec` 固化。_

### 4. 接口契约

本 feature **不以新业务 API 为默认交付**。若补洞涉及接口：

- 优先沿用现有 `/api/*`、`/ai/*`、`/health` 契约  
- 任何新增/变更 API 必须在 `/to-spec` 中显式写出，并证明映射到某条 E 的 P0  

数据模型：无强制 schema 升级；仅当 P0 必须时再开迁移。

_待 Plan 阶段细化。_

### 5. 实现步骤

_待 `/to-tickets` 拆票填充。_

建议票序（草案，非最终）：

1. S1：撰写公测章程 + 配置基线（E3/E4/E5/E7/E8 + E10 检查项标题）  
2. S2：发布 runbook + 备份与一次恢复演练（E1/E2）  
3. S3：双协议接入自助文档/入口打磨（E9）  
4. S4：故障感知与排查一页纸（E6/E7）  
5. 回归清单固化 + 发现即修的 P0 代码项  
6. 版本号与发布说明 → v0.1.0（`/smart-release`）  

### 6. 验收标准

- [ ] **E1** 发布/升级步骤成文；按文档可完成一次发布或演练；失败恢复路径明确  
- [ ] **E2** 备份任务可运行；至少一次恢复验证有记录  
- [ ] **E3** 公测默认可开渠道/协议/Coding Plan 规则成文  
- [ ] **E4** 开户/审核、停用、离职后 Key 不可用的责任与操作成文可执行  
- [ ] **E5** 默认日 Token 与打满行为已评审并写进基线  
- [ ] **E6** 健康检查 + 日志/管理端定位路径成文（最低配，不要求完整监控平台）  
- [ ] **E7** 工单或固定对接人 + 粗粒度响应预期成文  
- [ ] **E8** HTTPS/公司内使用边界、管理员与密钥规范成文  
- [ ] **E9** 新人可按文档完成 Claude Code 与 Cursor（或约定第二客户端）接入  
- [ ] **E10** 核心路径回归清单存在，且发布前可勾选执行  
- [ ] 无 0.1.0 排除范围（ROI/Commerce/SSO 等）被误纳入本版本必达  
- [ ] FEATURE_001 完成后，版本具备执行 `/smart-release` 升至 v0.1.0 的条件
