# v0.1.0 — Fabric · Token Hub 公测就绪

## Part A — 版本级叙事

### 版本目标

发布 **KodaX Fabric 核心模块 Token Hub** 的第一个「公司内可大范围公测」版本。

- 产品：KodaX Fabric  
- 本版本范围：仅 **Token Hub 核心模块**（仓库内既有 TokenHub 实现）  
- 基线：v0.0.5（`tokenhub.haizhi.com` 已可访问，已有同事用 Key + Claude Code）  
- 进度口径：Token Hub 进度 = Fabric 当前进度  

### 本版本范围

**做（0.1.0 must）**

将公测硬门槛 **E1～E10** 从「部分满足」收到「可签字验收」：

| ID | 门槛 |
|----|------|
| E1 | 可重复发布 |
| E2 | 数据可托底（备份 + 恢复验证） |
| E3 | 渠道策略成文 |
| E4 | 账号生命周期 |
| E5 | 配额默认合理 |
| E6 | 故障可感知（最低配） |
| E7 | 问题有入口 |
| E8 | 安全底线 |
| E9 | 接入可自助（双协议） |
| E10 | 核心路径不回退（回归清单） |

**裁剪原则（grill 冻结）**

- 落地类型：发布/公测就绪（非结构大拆、非先做大新功能）  
- 完成定义：**M5** — 生产/公测托底为主，只补挡住扩大使用的 P0  
- 清单裁法：**L4** — 公测准入为骨架 + 现网痛点；PRD 只拦 P0 安全/隔离/数据  
- 协议：双协议（Claude Code / Cursor 等）；一种工具建议一把 Key  

**不做（明确排除）**

- Token ROI / 浪费检测 / 文件归因  
- Budget Waterfall、Commerce、完整多租户组织  
- SSO、跨渠道容灾、协议互转  
- 为「更像 Fabric」而做的 monorepo 大目录重构（可用文档声明模块关系）

### 推荐收口顺序

```text
① S1 公测章程 + 配置基线成文     ← 第一刀
② S2 发布 runbook + 备份恢复演练
③ S3 接入自助（E9）打磨
④ S4 故障怎么查（E6）一页纸
全程：只修挡住公测的代码 P0
```

### 版本级验收

- E1～E10 均有可展示的验收证据（文档签字项、演练记录或自动化/清单勾选）  
- 现有 Claude Code（及约定的第二协议客户端）调用路径不回退  
- 版本号与发布说明将 Token Hub 表述为 Fabric 核心模块；不宣称 Fabric 全能力完成

### 1. 需求概述

#### Problem Statement

作为 **KodaX Fabric** 负责人，我已经把 **Token Hub 核心模块**（工程实现历史名 TokenHub，基线 v0.0.5）部署到 `tokenhub.haizhi.com`，并有同事用内部 API Key 在 **Claude Code** 中真实开发。但公测硬门槛 E1～E10 都只是「做了一些、不敢称完成」：

- 不知道下一步该加固运维、补文档，还是继续加功能  
- 不敢对全公司内部放开报名式使用  
- 容易把 Fabric 其它模块（ROI、组织、Commerce）误当成 0.1.0 必达  

核心用户问题不是「网关能不能转发」，而是：

> **如何证明 Fabric · Token Hub 已足够健壮，可以支撑公司内大范围公测，并清晰排除非本模块范围？**

#### Solution

发布 **v0.1.0 = Fabric · Token Hub 核心模块「公司内可大范围公测」完成态**（M5 + L4）：

1. **以公测准入 E1～E10 为验收骨架**，用成文证据把「部分满足」收到「可签字」  
2. **交付顺序固定**：S1 公测章程/配置基线 → S2 发布与备份恢复 → S3 接入自助 → S4 故障怎么查 → E10 回归走通 → 仅挡路的代码 P0  
3. **主交付 = 文档 + 运维演练 + 检查单**；默认不新增大功能、不改架构栈  
4. **叙事统一**：产品是 KodaX Fabric，本版本只宣称 Token Hub 核心模块就绪；工程包名可暂留 `tokenhub`  

#### User Stories

1. 作为 **负责人**，我想要一份写死范围与门槛的 0.1.0 定义，以便团队不再争论「健壮」指什么。  
2. 作为 **管理员**，我想要按公测章程开户/审渠道/设配额，以便扩大使用时配置不靠口头。  
3. 作为 **管理员**，我想要按发布 runbook 升级或恢复服务，以便变更可重复、失败可托底。  
4. 作为 **管理员**，我想要完成并记录一次数据库备份恢复演练，以便数据风险可交代。  
5. 作为 **管理员**，我想要渠道与 Coding Plan 默认策略成文，以便不会误开受限凭证池。  
6. 作为 **管理员**，我想要账号启停与离职后 Key 失效的操作说明，以便人员变动可执行。  
7. 作为 **管理员**，我想要默认日 Token 与打满行为写进基线，以便公测额度可预期。  
8. 作为 **管理员**，我想要一页故障排查路径（health + 日志/工单），以便有人报障时能定位。  
9. 作为 **员工**，我想要按双协议接入教程自助配置 Claude Code / Cursor，以便少打断管理员。  
10. 作为 **员工**，我想要明确的问题入口（工单或对接人）与粗粒度响应预期，以便知道找谁。  
11. 作为 **负责人**，我想要发布前可勾选的核心路径回归清单，以便扩大公测前做一次放行检查。  
12. 作为 **负责人**，我想要任何代码改动仅限挡住公测的 P0，以便 0.1.0 不被功能膨胀拖死。

### 6. 验收标准

#### Testing Decisions（seam = T1，已对齐）

**层 A — 主验收边界（本 feature 完成的充分条件）**

**层 B — 代码/回归辅助边界（有代码 P0 或做 E10 时）**

- **优先复用既有 seam**，不新建测试金字塔：  
  - 服务端单测/集成：配额日界与硬限、渠道隔离与 binding、relay 核心、工单隔离、健康相关既有用例

- **禁止**：为纯文档改动强制写单元测试；为 0.1.0 引入新的端到端框架
