# v0.1.2 — 单一企业三角色控制台

## Part A — 版本级叙事

### 版本目标

单一企业三档角色共用现有管理后台壳：企业管理员、团队管理员、开发者。按角色裁菜单和数据范围；开发者不再用简陋工作台。发钥跟角色走：开发者申请，团队管理员批本队，企业管理员可直接发但项目与池必须同团队。

切法：[../token-hub-slices.md](../token-hub-slices.md) **0.1.2**。  
手测对照：[../TokenHub_VISION.md](../TokenHub_VISION.md) **#17 #21 #24**（组织树 / 四角色 SaaS / 超管不做）。

### 本版本范围

**做**

- 三角色：`org_admin`（现 `admin` 正名）、`team_admin`、`developer`
- 操作员挂团队；列表与发钥按角色过滤
- 三角色共用 `/admin` 壳，按角色裁导航；撤掉 `/app` 卡片工作台
- 开发者：申请钥匙 + 自己的 VK 表 + 自己的审计 + 接口文档
- 团队管理员：本队用户 / 池 / 项目 / VK 发放与审批；**不看**上游钥匙、**不看**渠道
- 企业管理员直接发 VK 时，项目与池必须同团队；持有人可选，填了须同团队

**手测抓手**

- 开发者进不了上游钥匙 / 渠道 / 铺渠
- A 队管理员批不了 B 队的申请、看不到 B 队 VK
- 项目团队与池团队不一致则发不出去

**不做**

- 超管、多租户、Commerce、SSO
- 按角色重做 PRD 17 个大屏
- Embedding / Batch、Token ROI（0.2）

规格与票由 `/to-spec`、`/to-tickets` 填写，本文件 Add 时不写实现。

### 1. 需求概述

#### Problem Statement

控制台只有 `admin` / `developer`。管理员是本机总管，开发者只有一页卡片工作台。PRD 的发放链（申请 → 审批 → 绑项目 → 落到池）在界面上缩成「手选池 + 可选项目」，团队不参与人侧隔离。

#### Solution

单一企业三角色共用现有 `/admin` 壳，按角色裁菜单和数据。人挂上团队。开发者在同一壳里申请钥匙、看自己的表和审计、读接口文档；团队管理员批本队、管本队人/池/项目/VK；企业管理员管铺路和全公司钥匙。官方 Key 与渠道页只给企业管理员。登录后不再进 `/app`。

#### Out of Scope

- 超管 / SaaS 多租户 / Commerce / SSO
- 团队管理员只读渠道页；开发者管理池/渠
- Embedding / Batch / Token ROI
- 四角色裁 17 个大屏、工单系统、SSO

### 3. 技术方案

**D1 角色三值**  
`NormalizeRole` 只认 `org_admin` / `team_admin` / `developer`。读到遗留 `admin` 当作 `org_admin` 并在写回时改掉。不能删掉最后一个 `org_admin`。

**D2 权限看角色 + 团队，不看调用方头**  
列表/写操作从 session 里的操作员展开。忽略 body/query 里伪造的「我是别的队」。`withAuth(adminOnly)` 换成按动作鉴权，不再是「非 admin 一律 403」。

**D3 数据范围**  
- `org_admin`：全公司。  
- `team_admin`：只读/写本 `team_id` 的用户、池、项目、VK（VK 的项目或池属本队）。  
- `developer`：读本队项目/池（申请下拉用）、只读写自己的 VK 与自己 VK 的审计。  
上游钥匙、渠道、模型别名：仅 `org_admin`。

**D4 发钥与申请同团队**  
直接发放：`project.team_id == pool.team_id`，否则 400。`pool_id=0` / `project_id=0` 不再当通配。申请同样校验，且 `owner_id` 强制为申请人。审批人必须有权看到该申请（企管或申请所属队的队长）。

**D5 壳一样、菜单不同**  
导航按角色裁。开发者虚拟钥匙页是表格 +「申请钥匙」，不是卡片墙。接入说明放在接口文档，不单独占首页。

**D6 005/008 仍在其后**  
跨团队渠过滤、pending 不能调 `/v1`、明文只在批准/直接发放时一次，行为不变。

### 4. 接口契约

调用方 `/v1` 路径不变。控制台仍在 `/console/v1`。

**菜单**

| 页面 | org_admin | team_admin | developer |
|------|-----------|------------|-----------|
| 总览 | 全公司 | 本队 | 自己的钥匙 / 申请 |
| 用户 | 读写 | 本队读写 | 无（403） |
| 上游钥匙 | 读写 | 无（403） | 无 |
| 渠道池 | 读写 | 本队读写 | 无页面；申请时可列本队池 |
| 渠道 | 读写 | 无（403） | 无 |
| 虚拟钥匙 | 全公司发放 | 本队发放 / 审批 | 自己的表 + 申请 |
| 团队项目 | 全部 | 本队 | 无页面 |
| 路由审计 | 全部 | 本队 | 自己的调用 |
| 接口文档 | 有 | 有 | 有 |

**写操作（相对 0.1.1 的收紧）**

| 条件 | 行为 |
|------|------|
| 遗留 `role=admin` 登录 | `me.role` 为 `org_admin`，进 `/admin` |
| 开发者 `GET/POST` 上游钥匙或渠道 | 403，列表为空不是 200 伪装 |
| 队长对 B 队 VK / 用户 / 池 / 项目 | 读不到；写 403/404 |
| 队长批 B 队申请 | 403，申请仍 pending |
| `POST /virtual-keys` 缺项目或池，或两者不同队 | 400 |
| 开发者 `POST /virtual-keys` | 403；走 `POST /vk-requests` |
| 开发者申请缺项目/池，或跨自己的队 | 400；响应无 `secret` |
| 开发者申请成功 | 201，`status=pending`，无明文；`/v1` 拒 |
| 本队队长或企管批准 | 200，明文一次；之后 masked |
| 开发者 `GET /virtual-keys` | 只含自己的（含 pending） |
| 登录任意角色 | 进 `/admin/overview`；`/app` 重定向到 `/admin` |

官方 Key 明文仍不得出现在 `/v1` 或非发放响应。

### 6. 验收标准

#### User Stories

1. 作为企业管理员，我登录后进和现在一样的后台壳，能管全公司的路和钥匙。  
2. 作为团队管理员，我进同一套壳，只看见本队的人、池、项目、VK，进不了上游钥匙和渠道。  
3. 作为开发者，我进同一套壳，有总览、自己的 VK 表、申请按钮、自己的审计、接口文档，进不了铺路页。  
4. 作为开发者，我申请钥匙必须选本队项目和池，申请当时没有明文，pending 不能调 `/v1`。  
5. 作为团队管理员，我能批本队申请并看到一次明文，批不了 B 队。  
6. 作为企业管理员，我直接发放必须带同团队的项目和池，不能再「无项目」发出去。  
7. 作为平台，伪造「我是别的队」的请求头或 body 不改变范围。  
8. 作为调用方，005/008 的隔离、pending 拒绝、明文一次仍然成立。  
9. 作为遗留管理员，我的 `admin` 账号按企业管理员工作，不必重新注册。
