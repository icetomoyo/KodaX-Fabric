## FEATURE_002: 上游钥匙柜

> **状态**：**Completed**  
> **Spec**：已综合（T1，2026-08-13 用户确认「是」）  
> **Tickets / Implement**：#1–#4 **Done**

来源：[token-hub-slices.md](../token-hub-slices.md) 0.0.2 · [TokenHub_VISION.md](../TokenHub_VISION.md) #10 #12 #13 #14 · [HLD.md](../HLD.md) §3.4 / 加密 AES-256-GCM

### 1. 需求概述

#### Problem Statement

公司官方 Key 不能给员工看，也不能只以环境变量种子一把了事。同一家常买多把 Key，只打一把会先撞限流；某把 401 或额度没了，还继续砸上去会拖垮整摊调用。

管理员需要把 Key 放进网关（落盘加密）、同一家多把轮着打、废掉的不再被选。

#### Solution

在 001 的 VK→池→渠（渠绑一把 ProviderKey）上，把**官方 Key**做成可管理的钥匙柜：

- 入库走加密；列表和调用方响应永不出现明文。
- 同池、同协议、各绑一把 Key 的多条渠，健康请求按轮转摊开（不是挂了才换路）。
- Key 可标停用；上游对官方 Key 回 401/403（含额度拒绝）后，该 Key 停用，后续请求不再选它。

调用方仍只持 `fab-`，契约与 001 相同。

#### Out of Scope

- 按周期自动换新 Key、轮换中双 Key 热切（#11，0.0.8）
- 失败换路、优先级、权重抽签、路由审计（0.0.4）
- VK 过期、VK 模型白名单产品化（0.0.3）
- Key 级 RPM/TPM 配额账（#13 的限流配额；0.0.6 先做 VK RPM）
- 申请审批、操作台页面、四角色
- Redis 共享计数

### 2. 影响范围

| 区域 | 决策 |
|------|------|
| 身份形状 | 沿用 001：VK→池→渠→ProviderKey。一把官方 Key 仍只挂在一条渠上。禁止 VK 直接外键到官方 Key |
| 热路径 | 同协议多把 active Key 时轮转选用；停用的不入候选；401/403 后停用该 Key |
| 写入 | 管理侧能新增官方 Key、改 status；创建必须加密 |
| 存储 | `provider_keys` 已有密文和 status；001 解析已过滤非 active。本版补「写入、轮转、因 401/403 停用」 |
| 测试 | **只测 T1**（用户已确认）。管理录入在自动化里直接写 Store 夹具，不测登录页 |
| 页面 | 本版不做 |

### 3. 技术方案

**D1 加密是写入路径的硬约束**  
创建官方 Key 必须 AES-256-GCM 加密后落库（001 已有算法）。列表、错误体、调用方响应不得出现明文。解密只发生在出站打上游时。

**D2 多把 Key 的形状**  
同一 `provider_code` 允许多行。摊流量的最小形状：同池、同协议、两条（或更多）渠，各绑一把 active Key。不在一条渠上挂 Key 数组。

**D3 摊，不是 failover**  
健康请求在同协议 active 候选上**轮转**（轮次均摊）。本版不按权重抽签，不因 5xx 换下一条（那是 0.0.4）。只有一把 active 时行为与 001 相同。

**D4 废 Key 不再被选**  
`status != active` 的 Key 不进候选。人手改停用与自动停用同一套状态。候选被滤光：该协议 503，语义与 001「无匹配渠」相同，**不得**改打另一协议。

**D5 401 / 额度停用**  
上游用**官方 Key**回 401 或 403（含额度/权限拒绝）后，将该 Key 标停用。网络错误、5xx、调用方 4xx 不因此停用官方 Key。停用后同一把 `fab-` 的后续请求不得再打到这把官方 Key。

**D6 #13 本版收口**  
Key 有 label / status，可被停用。Key 级模型名单与 Key 级配额账本版不做（模型限制走 0.0.3 的 VK；配额走 0.0.6）。

**D7 管理写入不进 T1 主路径**  
手测可以 SQL 或之后的管理 API 塞两把 Key。自动化 T1 用 Memory/夹具预置两把 Key 和停用状态。本版不把登录、Cookie、操作台做成验收条件。

**D8 零转换与不泄漏不变**  
001 的 D1 / D8 / 不把 `fab-` 送到上游，全部保留。

### 4. 接口契约

调用方与 001 相同：

| 方法 | 路径 | 行为变化 |
|------|------|----------|
| POST | `/v1/chat/completions` | 同协议多把 active Key 时轮转；停用的不打 |
| POST | `/v1/messages` | 同上 |
| GET | `/health` | 不变 |

- 无匹配的 active Key：503，协议 envelope 与 001 一致。  
- 官方 Key 被 401/403 停用：当次可将上游状态/body 按 001 透传给调用方；**下一次**不得再选这把 Key。  
- 调用方 401 仍只表示 `fab-` 无效，与官方 Key 停用不是同一件事。

管理 HTTP 若本版附带实现，不得成为 T1 通过条件；且列表不得含 `secret` / `secret_encrypted`。

### 6. 验收标准

#### User Stories

1. 作为管理员，我把官方 Key 交给网关保存后，员工和列表都看不到明文，以便公司 Key 不外泄。  
2. 作为管理员，我为同一家录入两把官方 Key 并挂到同一池的同协议渠上，打流会摊到两把，以便不先打爆一把的限流。  
3. 作为管理员，我把一把 Key 标成停用后，新请求不再打它，以便废 Key 立刻退出。  
4. 作为平台，当上游对某把官方 Key 回 401/403 时，后续请求不再选它，以便失效/额度用尽的 Key 被摘掉。  
5. 作为开发者，池里只剩一把可用官方 Key 时，行为与 001 一样只打这一把，以便单 Key 种子不受损。  
6. 作为开发者，OpenAI 侧 Key 全停用时，Chat Completions 回 503，不会改走 Anthropic 渠，以便不跨协议。  
7. 作为开发者，我的 `fab-` 无效时仍是调用方 401，以便和「官方 Key 废了」区分开。

#### Testing Decisions

**缝 T1（已确认，2026-08-13）**：只在进程内 HTTP 上测网关：

- `POST /v1/chat/completions`
- `POST /v1/messages`

夹具直接写 Store：同协议两把官方 Key、或一把已停用。假上游按 Key 区分（例如不同 Secret 打到可观察的行为）。

测外部行为：

- 连续健康请求会打到两把 Key（摊），不是永远第一把。  
- 停用的 Key 一次都不会被打到。  
- 假上游对某把 Key 回 401/403 后，后续请求不再打这把。  
- 无 active Key → 503，且不打到另一协议的假上游。  
- 调用方响应/头不含官方 Key 明文（延续 001 不泄漏）。  
- 请求 body 仍零转换。

**不测**：读库看密文、登录页、操作台、5xx 换路、权重抽签、VK 模型名单。

**手测**（VISION #10 #12 #14；#13 本版只验「能停用」）：库或种子里两把 DeepSeek（或兼容）Key，`:3000` 连续打 Chat Completions 能摊；把一把 status 改停后不再打它。
