### 1. 需求概述

#### Problem Statement

开发者不应持有官方 Key，也不该为 GPT 和 Claude 各领一把钥匙。001 已经把协议绑在路径上、VK 不带协议字段，但产品上还没把「一把两端口」收成验收；试用/外包钥匙不能到期自废；实习生钥匙不能在钥匙上拦住贵模型。

#### Solution

调用方只持 `fab-`。同一把 VK 走 `POST /v1/chat/completions` 与 `POST /v1/messages`（池内该协议有活渠即可）。可设过期时刻：到期后按无效钥匙处理，401，不打上游。可设模型名单：名单非空时，请求 JSON 的 `model` 必须非空且在名单内，否则 403，不打上游、不推进该 VK 的渠轮转。空名单 = 不限模型。

#### Out of Scope

- 申请审批、IP 白名单、明文只亮一次的申请流（0.0.8）
- 组织树 / 项目实体（0.0.5）
- `x-fabric-context` 的业务语义（本版只预留：头可出现，网关忽略）
- 模型别名、同协议 failover、权重主备（0.0.4）
- 管理后台表单必须能改过期/名单（T1 不测操作台；控制台补字段不挡本 feature）
- Token ROI / Commerce / SSO

### 3. 技术方案

**D1 一把两端口是验收，不是新形状**  
001 的 D2 已定：协议在路径上。本版用同一把 `fab-` 打通两个端点作为验收（池内两协议各有活渠）。不得给 VK 加「仅 OpenAI / 仅 Anthropic」。

**D2 过期**  
`expires_at` 为空：不因时间拒绝。非空且 `now >= expires_at`（含恰到期）：401，错误 envelope 与无效 VK 相同（该端点原生），**不打上游**。过期不是 403。

**D3 模型名单**  
名单空或不存在：不限。名单非空：必须先读请求 JSON 的 `model`（精确字符串相等，不做别名展开），再选渠。`model` 缺失、空、或不在名单 → 403，语义 `model_not_allowed`，**不打上游**，**不推进**该 VK+协议的轮转下标。在名单内则继续 002 的选渠。

**D4 检查顺序**  
鉴权（无/假 `fab-` → 401）→ 过期 → 模型名单 → 选渠。过期优先于模型，避免过期钥匙还因模型报 403。

**D5 可测时钟**  
过期用可注入时钟，T1 不依赖墙钟。

**D6 预留头**  
`x-fabric-context` 可出现，本版不解析、不拒绝、不改变路由。

**D7 002 行为保留**  
官方 Key 401/403 停用、同协议摊流、不跨协议、不泄漏官方 Secret、零转换，全部保留。

---

### 4. 接口契约

调用方路径与 001 相同。

| 条件 | HTTP | 语义 | 上游 |
|------|------|------|------|
| 同一把有效 `fab-`，池内有对应协议活渠 | 透传上游 | 两端点都能用 | 打 |
| `expires_at` 已到或已过 | 401 | 与无效 VK 同 envelope | 0 |
| 名单非空且 `model` 空/缺/不在名单 | 403 | `model_not_allowed`（Anthropic 用该端点 error envelope，文案同等） | 0 |
| 名单非空且 `model` 在名单 | 继续选渠 | — | 按 002 |
| 名单空 | 不因模型拒绝 | — | 按 002 |

- OpenAI：`Authorization: Bearer fab-…`  
- Anthropic：`x-api-key: fab-…`（仍接受 Bearer）  
- 响应与错误体仍不得出现官方 Key 明文。

### 6. 验收标准

#### User Stories

1. 作为开发者，我用同一把 `fab-` 打 Chat Completions 与 Messages 都能通（池内两协议各有活渠），以便不为两个客户端各领一把钥匙。  
2. 作为平台，VK 到期后该钥匙再调任一端点都是 401，且上游 0 次，以便试用/外包钥匙自己作废。  
3. 作为平台，`model` 不在该 VK 名单时得 403，上游 0 次，以便贵模型在钥匙上拦住。  
4. 作为开发者，`model` 在名单内时行为与 002 一样能打通，以便白名单不是误伤合法调用。  
5. 作为开发者，名单为空时任意 `model` 都不因名单被拒，以便默认钥匙不额外设限。  
6. 作为平台，名单非空但请求没有 `model`（或字段为空）时也是 403、上游 0 次，以便漏写模型不能绕过。  
7. 作为开发者，伪造或未知的 `fab-` 仍是调用方 401，以便和「官方 Key 废了 / 模型不允许」区分开。

#### Testing Decisions

**缝 T1（已确认，2026-08-13）**：只在进程内 HTTP 上测网关：

- `POST /v1/chat/completions`
- `POST /v1/messages`

夹具直接写 Store：同一把 VK 挂两协议渠；另备已过期 VK、带模型名单的 VK。假上游可观察是否被打到。过期用例拨注入时钟，不睡墙钟。

测外部行为：

- 同一 `fab-` 两端点均可 200（假上游固定成功体）。  
- 过期 → 401，假上游命中 0；envelope 与无效 VK 同类。  
- 名单外 / 缺 `model` → 403，上游 0；名单内 → 打到上游。  
- 空名单不因 `model` 拒绝。  
- 拦截时轮转下标不前进（两把同协议渠时，被拒请求不改变下一把该打谁）。  
- 请求体仍零转换；响应不含官方 Secret。

**不测**：读库、登录页、操作台表单、模型别名、failover。

**手测**（VISION #6 #16 #20 #22）：同一把 VK 在 Cursor（Chat Completions）与 Claude Code（Messages）都能通；把过期或模型名单配上后，对应请求被拒且不打上游。
