### 1. 需求概述

#### Problem Statement

研发的调用不该去烧市场那把官方 Key。现在 VK 已经挂在一个池上，但池、渠、官方 Key 没有团队归属，查询时只要在同一个池就能打到任意 Key。两把钥匙也无法从产品上证明「走的是不同摊路」。VIP / 普通 / 跑批也分不出 premium / standard / bulk。

#### Solution

链路定为 **VK → Project → Team → ChannelPool → Provider Key**。调用方不能用 header 指定团队或池，一律从 VK 解析。查询层只返回：渠的池 = VK 的池，且池、项目、官方 Key 的团队一致。无团队归属的旧夹具（团队=0）只能打同样无归属的池和 Key。池有分组 premium / standard / bulk，写进审计和响应头。

#### Out of Scope

- 限流熔断（0.0.6）
- 申请审批、IP 白名单（0.0.8）
- 完整组织树、四角色控制台、SSO
- 调用方自选池/组
- Token ROI / Commerce

### 3. 技术方案

**D1 解析只信 VK**  
团队、项目、池全部从 VK 展开。忽略调用方传入的 team/pool/group 头或 query，避免越权。

**D2 查询层隔离**  
候选渠必须同时满足：`channel.pool_id = VK.pool_id`，且 `pool.team_id = project.team_id = provider_key.team_id`。`pool_id = 0` 不是通配。错挂在 A 池里的 B 团队 Key 不得入选。

**D3 无归属**  
team_id=0 表示未分团队。无归属 VK 只能打无归属池+无归属 Key。有团队的 VK 打不到 0，也打不到其他团队。

**D4 两 VK 两池**  
两把有效 `fab-` 绑不同池时，各自只打到本池假上游，互不串。

**D5 分组**  
`group_name` 仅允许 `premium` / `standard` / `bulk`（缺省 standard）。成功或最终失败响应可带池分组与团队 id，审计记录同样带上。

**D6 004/003 仍在其后**  
隔离过滤之后，才走 003 过期/名单和 004 主备/换路。跨团队 Key 被滤掉后，不得为了 failover 再把它捞回来。

---

### 4. 接口契约

调用方路径与鉴权不变，不能靠请求指定池或团队。

| 条件 | 行为 |
|------|------|
| VK-A 绑池 A，VK-B 绑池 B | 各打各池；A 的请求 0 次命中 B 的假上游 |
| A 池误挂 B 团队官方 Key | 该 Key 永不被 A 的 VK 选中 |
| 无归属 VK + 仅有团队 Key | 无匹配渠 → 该端点 503 |
| 分组已设 | 响应可见分组（如 `X-Fabric-Pool-Group`） |

官方 Key 明文仍不得出现在调用方响应。

### 6. 验收标准

#### User Stories

1. 作为平台，两把 VK 走不同池，各自只打到本池线路，以便账单能拆开。  
2. 作为平台，A 团队请求打不到 B 的官方 Key，即使有人把 Key 错挂进 A 的池。  
3. 作为开发者，我不能在请求里改团队或池来越权。  
4. 作为平台，池的 premium/standard/bulk 能在响应/审计里看到，以便证明走的是哪档路。  
5. 作为开发者，001–004 的无团队种子行为仍通（team=0 打 team=0）。

#### Testing Decisions

**缝 T1（已确认，2026-08-13）**：进程内 `POST /v1/chat/completions`（Messages 用同一套隔离，抽一条覆盖即可）。

夹具：Team A/B、两项目、两池、两把官方 Key、两把 VK。假上游按 Key 区分。

测外部行为：

- VK-A 连续请求只命中 A 的 Key。  
- 把 B 的 Key 挂进 A 池后，VK-A 仍 0 次打到 B。  
- 伪造 team/pool 头不改变命中的 Key。  
- 成功响应含池分组。  
- team=0 旧形状测例仍绿。

**不测**：读库、登录页、四角色 UI、限流。
